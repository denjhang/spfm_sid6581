# SPFM 时序精度的上限 —— 为什么 SID 播放到此为止

> 结论文档。写给以后想"再优化一下时序"的人：**没有可优化的了。**
> 不是驱动写得不够好，是 SPFM 协议本身不给这个能力。
> 硬件依据见 [驱动说明.md](驱动说明.md)，链路数字见 [SPFM链路预算与降速分析.md](SPFM链路预算与降速分析.md)，
> 早期排查过程见 [写入时序调试记录.md](写入时序调试记录.md)。

## 0. 一句话结论

**SPFM 是给雅马哈 YM 系列设计的"写入数据流"协议，主机侧没有引脚控制能力，
也没有 PHI2 概念。SID 的寄存器播放，在现在这套驱动上已经达到协议允许的精度上限。**

- digi（`$D418` 数字鼓）靠 `--pad` 用 NOP 字节填缝，够用，因为它的间隔远大于刻度。
- 普通 PSID 的帧内时序抖动 **无解**，并且在 SPFM 框架内**不可能有解**。
- 想再往前一步，不是改驱动，是换协议（见 §5）。

## 1. 协议只给主机三样东西

打开 `src/spfm_transport.h`，主机能发的字节形态只有这些：

| 形态 | 字节 | 主机表达了什么 |
|---|---|---|
| Path A | `[slot, 0x00, addr, data]` | 哪个槽、哪个寄存器、什么值 |
| Path B | `[slot, 0x80\|n, data]` | 同上，A0..A3 编进命令字节 |
| NOP | `0x80` | "多过一个 tick" |

这三样里**没有任何一项是"把某根线拉高/拉低/翻转"**。
`/WR`、`/CS`、`A0` 的电平变化全部发生在 STM32 固件收到包之后，由固件自己产生。
主机既不能指定它们何时变化，也不能读回它们现在是什么状态——这套协议没有回读通道。

这正是它作为 YM 写入流的设计本意：YM2163 / YM7129 只认
"`/CS` + `/WR` 下降沿 + 地址数据"，固件连发两个总线周期就够，没有人在意间隔。
反过来，SID 是唯一需要"写动作落到时钟节拍上"的芯片，于是差距全在这里。

## 2. 因此这三件事在 SPFM 上做不到

| 做不到的 | 原因 |
|---|---|
| **PHI2 挂钩** | NOP 数的是固件循环，不是 PHI2 边沿。主机连"当前 PHI2 处在第几个周期"都无从得知，谈不上"等到下一个上升沿再写" |
| **亚字节精度延时** | 主机唯一的刻度是一个线字节 = 6.667 µs，只能用 NOP 去凑。USBSID 那个 16 位 cycle 字段能用，是因为板上 PIO 直接数 PHI1；我们连"数"这个动作都无处安放 |
| **准点发生** | 主机只能控制字节何时交给 FT232R，真正的总线动作时刻由固件在自己方便的时候执行。USB 帧调度（1 ms）、驱动 buffer（2 ms latency timer）、固件主循环叠加之后，主机既测不准也补不回 |

补充一条容易忽略的：**Path A 两相之间的间隔不可控也不可测。**
它由 STM32 固件连发，我们不知道隔多久，也无法调。
只能在 Path B 模式下自己插 NOP 去替代它。

## 3. 为什么 `--pad` 有效，而它救不了 PSID

`--pad` 的原理是把写间隔钉在 UART 移位时钟上：注入 NOP（`0x80`），
让线上字节的物理间距直接复现目标间隔，绕开主机 `Sleep` 的 1 ms 量化。

它成立的前提是**目标间隔远大于刻度**：

| 场景 | 目标间隔 | 刻度 | 量化误差 | 结果 |
|---|---|---|---|---|
| digi 的 `$D418` | ~136 µs | 6.667 µs | ~5% | 听不出来，`--pad` 成立 |
| 普通 PSID 的帧内节奏 | 微秒级，且要求相序 | 6.667 µs | 与信号同量级 | 被抹平或推歪，`--pad` 反而有害 |

早期版本给整首曲子无差别加 pad，结果普通段落"卡顿、节奏异常"，
就是这个道理——**在一个比信号还粗的格子上做量化，只会破坏信息。**
所以后来加了密度闸门（`--pad-rate` / `--pad-hold`），只在 `$D418` 密集段启用。

但闸门只是把伤害限制住，**不能把精度提上去**。
PSID 要的是"这一帧里这 50 个写按 6502 的节奏依次落下"，而 6502 的节奏本身就在微秒级。
落在 6.667 µs 的格子上，必然有一部分写被提前、一部分被推后，
相位关系（哪些写挨在一起、间隔多久）无法保住。
这不是参数调优问题，是采样定理问题。

## 4. 和 USBSID-Pico 的对照（为什么不建议在 SPFM 上继续投入）

| | USBSID-Pico | 本项目（SPFM） |
|---|---|---|
| PHI2 来源 | 板子 PIO 分频产生（`pio.c`），或外部时钟进 PIO 镜像（`clock_link.pio`） | 模块自带 can 晶振，1.000 MHz，总线看不到 |
| 写与 PHI2 的关系 | **定相**：`bus_control.pio` 每条指令都卡在 PHI2 边沿 | **无关系**：字节到了就写，相位随机 |
| 时间信息载体 | 包内 16 位 cycle 字段，板上 delay 状态机数 PHI1 执行 | 协议里没有这个字段，只能主机插 NOP |
| 时间精度 | 1 µs，抖动为零 | 6.667 µs（NOP）或 ~1 ms（`Sleep`） |
| 主机可提前多少 | 板上队列 4096 条写 / 8 个 USB 包，可整秒预灌 | 无板载队列，积压只能靠主机自己控（`--pad-window` 补偿的正是这个） |
| 实测写速率 | 约 94 000 写/s | 37 500 条/s（150 kB/s 线速 ÷ 4 字节） |

关键差别只有一句：**USBSID 把时间放进包里，由执行端用自己的时钟兑现；
SPFM 没有这个字段，时间只能留在主机侧，而主机侧的时钟比 SID 粗三个数量级。**

顺带记一个数字，避免以后误判：USBSID 源码里的 `MIN_CYCLES = 6`、
ASID 的"至少 10 cycles"（`asid.c:72`，注释 "Pico 2 requires at least 10 cycles
between writes or it will be too damn fast"）**都不是 SID 的要求**，
那是 RP2040 PIO + DMA 流水线追不上的下限。6581 数据手册只有 `TW ≥ 350 ns`
的脉宽要求，没有任何写间隔要求——这一点我们已在
[写入时序调试记录.md](写入时序调试记录.md) §9 上机证实。

## 5. 如果确实要继续，路只有一条

**换掉主机与 SID 之间的控制器**，让产生 PHI2 的那个东西同时也能数 PHI2。
候选：

1. **自绘 RP2350 板**，保留 74LS374 三颗 IC 的地址锁存方案（这套已验证有效，
   而且 374 把地址锁死了，两相间隔对地址稳定性毫无影响）。
   固件自己定义带 cycle 字段的包，PIO 数 PHI2 执行。
   多槽 YM 也留在同一块板上——这是唯一能同时服务 SID 和 YM 的方案。
2. **SID 交给现成的 USBSID-Pico**，SPFM 专心跑雅马哈。
   最省事，代价是两块板分工，且 SID 侧不能再跟 YM 同板混跑。

两个前提条件，无论走哪条：

- **PHI2 仍然由独立晶振供给，只额外引一根线进 MCU 的 GPIO 让 PIO 数边沿。**
  不要让 MCU 输出 PHI2：MCU 复位或跑飞 = SID 时钟停摆，而且音高要跟着重标定
  （现在的 `SID_PHI2_HZ_DEFAULT = 1000000.0` 本来就是个近似值，
  PAL/NTSC 应该是 985248 / 1022727 Hz）。
- **保留 374 方案不需要任何改动。** 逻辑照旧：`A0=0` 锁地址，`A0=1` 写入；
  `TRIG_n = ¬A0 ∨ /WR ∨ CSn` 只驱 `/CS`，`R/W` 单独接 `/WR`。

## 6. 所以现在该停在哪里

| 项目 | 状态 |
|---|---|
| 单次写入稳定、音高正确 | ✅ 已解决（三颗 IC，见接线表） |
| digi 的 `$D418` 时机 | ✅ `--pad` + 密度闸门，误差 ~5%，听觉上成立 |
| 普通 PSID 的帧内时序抖动 | ❌ **协议上限，无法解决** |
| 链路带宽 | ✅ 最重曲目平均 17.9%、峰值帧 38%，余量 4–5 倍 |
| 写速率上限 | 37 500 条/s，由 150 kB/s 线速决定，不可提升 |

**在这个硬件上，SID 驱动的开发工作已经结束。**
再出现"节奏不对"的反馈，正确的回应是解释这是协议精度上限，而不是继续加参数。
