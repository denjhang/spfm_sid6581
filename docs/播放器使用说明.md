# 播放器使用说明（PowerShell）

当前构建：`build\sidtest.exe`，一个 exe 里带三件事——寄存器冒烟测试、`.sid`
文件播放、离线寄存器流抽取。全部命令都在 PowerShell 里跑，路径用
`E:\working\zcode-projects\spfm_sid6581`。

**只想听音乐请用 `build\spfmplayer.exe`**（见
[docs/播放器_spfmplayer.md](播放器_spfmplayer.md)）：它支持 `.sid` /
`.sidvgm` / `.sidreg` / 目录，`.sid` 默认走 libsidplayfp，digi 鼓和真 RSID
都对。本文档讲的是 `sidtest.exe`，那是上机调试工具。

`sidtest.exe` 的 `sidplay` 也能播 `.sidvgm` 和 `.sidreg`（按录制的时间线回放，
不再跑 6502），`.sid` 则走内置 6502，用于离线录制和两套核心的对照。

### sidtest 的边界（重要）

**`sidtest.exe` 的行为是冻结的，新增的只是"认识一个文件格式"。**

| 输入 | 走的代码 | 和以前比 |
|---|---|---|
| `.sid` | 内置 fake6502（`sid_rsid.c`）→ 现有 `replay()` | **完全不变**，一个字节都没改 |
| `.sidvgm` | `sidvgm_read()` 读容器 → 同一个 `replay()` | 新增，但复用的是 `.sidreg` 现成的回放路径 |
| `.sidreg` | `sid_sidreg_read()` → 同一个 `replay()` | 完全不变 |

具体说：

- **不链接 libsidplayfp。** `sidtest.exe` 里没有任何 lsfp 代码，它还是纯 C +
  fake6502。想用 libsidplayfp 只有 `spfmplayer.exe`。
- **不特殊处理 RSID。** `sidplay.c` 里没有 `is_rsid` 判断，RSID 和 PSID 走
  同一条老路：`sid_rsid.c` 每帧调一次 `play()`，`play=0000` 的头靠
  `$FFFE` / `$0314` 两个向量去猜入口。这些行为**一个字都没动**。
- `.sidvgm` 只是"已经录好的寄存器流"，播放时和 `.sidreg` 完全一样：按时间戳
  把写入推出去。它不改变任何时序策略、不改变写入协议、不改变 flush 逻辑。

换句话说：`sidtest` 仍然是那个"照旧"的调试工具，只是因为多了个容器读取函数，
现在也能直接播预渲染文件了。

**但要注意 `.sidvgm` 里的内容是别人录的。** `sid/` 里的文件用
`sidextract --engine lsfp` 转成 `sidvgm/`（见第 4.1 节），所以 digi 鼓和真
RSID 的节奏**已经录进文件里**了。`sidtest` 回放时不需要理解这些——它只是
照着时间戳把写入推出去。差别来自录制端，不来自播放端。

## 1. 先确认设备和芯片

```powershell
cd E:\working\zcode-projects\spfm_sid6581
.\build\sidtest.exe list
```

输出会列出 FTDI 设备序号和描述，正常只有一个（序号 0）。没有输出说明
DLL 或驱动没就位：`build\ftd2xx64.dll` 必须和 exe 在同一个目录。

SID 接在 **slot 3**（RE-SPFM 最后一个槽）。要换槽就加 `--slot N`，
N 取 0..3。

## 2. 播一首 `.sid`

```powershell
# 一直播到按键；n = 下一首，q = 退出
.\build\sidtest.exe sidplay sid\Golden_Axe.sid

# 只播 60 秒
.\build\sidtest.exe sidplay sid\R-Type.sid --seconds 60

# 换子曲（从 0 数起）
.\build\sidtest.exe sidplay sid\R-Type.sid --subsong 3

# 1.5 倍速
.\build\sidtest.exe sidplay sid\R-Type.sid --speed 1.5
```

播放时屏幕右下角每秒刷一行，`lag` 是这一秒里写事件最晚到多久。正常是
0～2 ms；持续几十毫秒说明定时器或 USB 被抢了。

按键：

| 键 | 作用 |
|---|---|
| `n` | 跳到下一首 |
| `q` / `Esc` | 退出 |
| `,` / `.` | 上一个 / 下一个子曲（只在 `sidlist` 里有效） |

### 换一首歌之前要知道的两件事

`--seconds 0`（默认）是**无限播**：6502 边跑边推，不预渲染，所以不会像
以前那样 60 秒就停。给了 `--seconds N` 就变成先渲染 N 秒再回放，用于快速
比对或做实验。

第一次播某个文件会顺手把渲染结果缓存到 `sid_cache\`，第二次启动明显更快。
缓存内容和 `--seconds` 绑定，换时长就会重新渲染。

## 3. 定时器 / 发送模式（新）

这两组参数是本轮从参考播放器移植过来的，默认值就是推荐值。

### 3.1 定时器 `--timer`

| 值 | 行为 | 适用 |
|---|---|---|
| `hprec`（默认） | 常驻高精度 waitable timer，配合 1 ms 系统计时精度 | 日常播放 |
| `hybrid` | 先 `Sleep()`，最后 1 ms 忙等 | 机器负载轻、想要更紧的时间 |
| `mmtimer` | 每次 `timeSetEvent(1 ms)` 一次性定时器 | 排查 waitable timer 问题时用 |
| `vgmplay` | 1 ms 周期多媒体定时器事件，不忙等 | CPU 占用最低，抖动约 1 ms |

```powershell
.\build\sidtest.exe sidplay sid\Golden_Axe.sid --timer hprec
.\build\sidtest.exe sidplay sid\Golden_Axe.sid --timer hybrid
.\build\sidtest.exe sidplay sid\Golden_Axe.sid --timer vgmplay
```

### 3.2 发送粒度 `--flush`

| 值 | 行为 |
|---|---|
| `command`（默认） | 一帧的寄存器写攒成一个 USB 批量，在帧边界发出去 |
| `register` | 每写一个寄存器就单独发一次 USB 传输 |

`command` 是给 C64 曲子的正常用法：播放例程一帧内写完 50 个寄存器，然后
静默 20 ms，批量正好落在静默里。`register` 更"准"但每个写都要等一次
2 ms 的 FTDI latency，只在一帧写得很少、或者要逐字节比对波形时用。

```powershell
.\build\sidtest.exe sidplay sid\Golden_Axe.sid --flush register
```

### 3.2b 传输节奏 `--flush-gap`（digi 曲目变闷时用）

这是**唯一**决定 digi 曲子在自己这一侧要付多少次 USB 传输的参数。

默认规则是"下一个事件离得够远才发批"（阈值 4 tick = 0.09 ms）。C64 数字鼓每
136 µs 写一次 `$D418`，比阈值长，所以几乎每条事件都触发一次传输：Giana 第 1 子曲
实测 **5362 次传输/秒，平均 4.4 字节**。FT232R 是全速 USB，主机控制器对一个 bulk
端点每个 1 ms 帧只排一次传输，**实际天花板约 1000 次/秒**。超出的部分堆在驱动队列里，
按 USB 帧的粒度成团吐出，136 µs 的鼓点分辨率塌成 1–2 ms —— 听感就是"发闷、
像被降采样过"。数据量本身没问题（28.6 kB/s，只占 150 kB/s 的 19%）。

`--flush-gap MS` 改成"一批至少要攒够 MS 的流时间才发"，把传输次数压下来：

| `--flush-gap` | Giana s01 传输/秒 | 平均每批 |
|---|---|---|
| 默认（0.09 ms） | 5362 | 4.4 B |
| `1` | 914 | 26 B |
| `2` | 432 | 55 B |
| `5` | 176 | 134 B |
| `10` | 93 | 255 B |
| `0` | 只靠 64 KiB 缓冲（诊断用，整段一起传） | — |

```powershell
# digi 曲目：先试 2，再按需往 1 或 5 调
.\build\sidtest.exe sidplay sidvgm\rsid\Echoes.sidvgm --flush-gap 2
.\build\sidtest.exe sidlist sidvgm --flush-gap 2
```

代价：一批攒 2 ms 意味着 2 ms 内的写入一起到达，鼓点的时间分辨率就是 2 ms。
所以这不是"无损提速"，是在"传输次数"和"鼓点分辨率"之间选点。默认值保持不变，
普通 PSID 曲子（事件本来就一帧一批）不受影响。

每次播放结束会打印一行，用来判断有没有超：

```
  link: 8633 transfers (432/s), 472064 bytes, avg 54.7 B, largest 120 B
```

`transfers/s` 在 1000 以下就是安全的；超过 1000 说明还在被 USB 帧粒度限制。

### 3.2c 反向方案 `--pad`：用 UART 时钟自己走时间

`--flush-gap` 是"攒得更粗"，所以鼓必然变钝。`--pad` 是反方向，而且不需要主机
时钟参与。

1.5 Mbaud 8N1 下 **1 字节 = 6.667 µs**，这是 UART 自己产生的、USB 调度干扰不到
的时间基。鼓点间隔 136 µs = 20.4 字节，Path A 命令只占 4 字节，剩下约 16 字节用
NOP（`0x80`）填满即可——NOP 不写任何寄存器，固件只是空转消耗时间，SID 什么也
看不到。于是：

- 136 µs 的间距由线上字节精确复现，不再取决于主机能否按时唤醒；
- 主机只需要保证不透支，传输次数从 5362/s 掉到 **2/s**。

占空比是唯一的约束。Giana s01 实测（20 秒）：

| 参数 | 线上占用 | 传输/秒 |
|---|---|---|
| 默认 | 16% | 5362 |
| `--pad 0.3` | 66% | 2 |
| `--pad 0.3 --pad-duty 50` | 47% | 1 |
| 补满所有间隔（不可用） | 98–100% | — |

`--pad` 会自动打开 `--dedup-vol`（丢掉与"芯片当前已锁存值"相同的 `$D418` 写入）。
这是能让占空比降到可用的关键：Giana 有 66% 的 `$D418` 是重复值，芯片本来就保持
那个电平，删掉听不出区别。去掉重复后同样的 136 µs 间距只要 27% 线速。

```powershell
# digi 曲目：先试 0.3，看结束那行的 wire%，超过 85% 就调小
.\build\sidtest.exe sidplay "sidvgm\Great_Giana_Sisters-rsid\Great_Giana_Sisters-rsid_s01.sidvgm" --pad 0.3
.\build\sidtest.exe sidlist sidvgm --pad 0.3 --pad-duty 50
```

`--pad MS` 只补 ≤ MS 的间隔；更长的静音由主机自己等，所以曲子总时长不会变。
`--pad` 和 `--flush-gap` 不要同时用（`--pad` 会接管节奏）。

结束那行会多一个 `wire NN%`：

```
  link: 972 transfers (49/s), 1988590 bytes, avg 2046 B, largest 2048 B, wire 66%
```

超过 85% 会直接提示，那说明填充挤占了下一段爆发要用的空闲。

#### `--pad-window` / `--pad-local`：治"速度不均匀"

你听到的"pad 越大音质越好但曲子速度不均匀"，原因不在填充本身，而在**局部超支**。
线上 1.5 Mbaud = 150 kB/s，而鼓点在某 20 ms 内可能要求比这更多。全局的
`--pad-duty` 是按整首平均的，看不见这种局部尖峰：平均 56% 的一首，某些 20 ms
窗口会顶到 105%。一旦某个窗口超 100%，那段时间的字节就排不下，`FT_Write` 开始
阻塞，主机错过下一个 `due`，**整首就被往后推**——听感就是忽快忽慢。

修法是加一个**滑动窗口**上限：任意 `--pad-window` 毫秒的音乐里，填充只允许占到
`--pad-local` 百分比。超了就当场拒绝这一处填充（该间隔退回主机计时），而不是让
它透支。

```powershell
# 每 100 ms 内最多用 80% 线速；尖峰处拒绝填充，其余照旧
.\build\sidtest.exe sidplay "...turboutrun_s01.sidvgm" --pad 1 --pad-window 100 --pad-local 80
```

实测 turboutrun s01（20 秒）：

| 参数 | 平均线速 | 被拒的间隔 |
|---|---|---|
| `--pad 1` | 56% | 145 |
| `--pad 1 --pad-window 100 --pad-local 80` | 55% | 834 |

被拒数量上升是**好事**：说明上限在尖峰处真的起了作用，而不是让它们累积成迟到。
`--pad-window 0`（默认）关闭该功能。

结束行会多一行：

```
  pad: 9427 ms filler, 834 gaps refused
```

#### 延迟与缓冲

填充模式产生字节的速度远快于 1.5 Mbaud 消费，所以必须限制"允许多少字节在前面排队"：

| 项 | 值 |
|---|---|
| 每次 flush 的分块 | 2 KiB = 13.6 ms 线上时间（默认模式下仍是 64 KiB） |
| 主机领先音乐的上限 | 25 ms |
| 端到端延迟 | 约 40 ms |
| 切曲 | 先丢弃未发完的队列再静音，不会拖着上一首的尾巴 |

不这么做的话，64 KiB 缓冲意味着每次 flush 后面压着 437 ms 的音频：开始播放要等
半秒才出声，切曲要等这半秒放完，而且大块 `FT_Write` 会把驱动队列堵死——表现就是
"只有切曲瞬间有声音，播放时没有数据下发"。现在 `FT_Write` 短写也不再丢弃剩下的
字节，而是等驱动腾出空间继续发。

#### 四个可调参数（按出现问题的顺序调）

| 参数 | 默认 | 作用 | 什么时候动它 |
|---|---|---|---|
| `--pad` | 关 | 补填充的最大间隔 | 决定鼓能好到什么程度；越大越接近原音 |
| `--pad-duty` | 75 | 填充最多占多少线速 | 密集段落顶满、出现断续时下调 |
| `--pad-lead` | 25 ms | 主机领先音乐多少 | 延迟太大就调小（10–15）；出现断音就调大（40–60） |
| `--pad-chunk` | 2 KB | 每次 flush 的块大小 | 调大减少传输次数、增延迟；调小反之 |
| `--pad-burst` | 200 ms | 漏桶能攒多少 | 调小让填充更均匀但鼓更稀；一般不用改 |

**判断依据只有三个数**：结束行的 `wire`、`largest B`，和耳朵听到的断音。

#### `--digi HZ`：只管数字鼓的采样率

这是**真正决定鼓音色**的参数，和 `--pad` 无关。

数字鼓就是一条 `$D418` 写入流。`--digi HZ` 把这些写入按 1/HZ 秒的时间格重新采样：

- 同一格里后来的值覆盖前面的（采样保持，等于 DAC 在那个窗口结束时停的电平）
- 和芯片当前已锁存值相同的写入直接丢掉（芯片本来就保持那个电平）
- **其它 24 个寄存器一条都不动**，时间戳保持原来的时间基，曲子总长度不变

```powershell
# 只降鼓的采样率，不动填充、不动旋律
.\build\sidtest.exe sidplay "...turboutrun_s01.sidvgm" --digi 4000

# 降采样 + 填充：鼓准、传输少，代价是 wire 上去
.\build\sidtest.exe sidplay "...turboutrun_s01.sidvgm" --digi 4000 --pad 0.25
```

实测 turboutrun s01（20 秒，不加 pad 时）：

| `--digi` | `$D418` 保留 | 传输/秒 |
|---|---|---|
| 关 | 3637/s | 3707 |
| `8000` | 2197/s | 2292 |
| `6000` | — | 2173 |
| `4000` | 1698/s | 1803 |
| `2000` | 1042/s | 1164 |

Giana s01（`$D418` 原始 6625/s，其中 66% 是重复值）：

| `--digi` | 保留 | 传输/秒 |
|---|---|---|
| 关 | 6625/s | 5362 |
| `8000` | 1652/s | 1766 |
| `4000` | 1155/s | 1290 |
| `2000` | 676/s | 830 |

结束时会多打一行：

```
  digi: 73702 $D418 in -> 43944 out (2197/s), 760 merged, 28998 duplicate-dropped
```

`merged` 是被同格覆盖的，`duplicate-dropped` 是被判为重复值丢掉的。前者是真的丢信息
（决定音质），后者无损。

**`--digi` 和 `--pad` 是两个独立维度**：

|  | 不加 pad | 加 pad |
|---|---|---|
| 鼓音色 | 由主机调度精度决定（差） | 由 UART 字节时钟决定（好） |
| 瓶颈 | 传输次数（1 ms USB 帧） | 线速占空比 |
| 调法 | 降 `--digi` | 降 `--digi` 或降 `--pad-duty` |

如果**不加 pad 但加 `--digi`**，鼓依然会闷（主机计时的问题没解决），只是传输次数下来了。
如果**加 pad 但不加 `--digi`**，鼓很准但线速吃紧（turbo 上 `--pad 0.3` 到 60%）。
两个一起用是最优：`--digi 4000 --pad 0.25` 在 turbo 上是 37% 线速、27 次传输/秒。

### turboutrun 这类"压力大"的曲目

turboutrun s01 和 Giana 不是一个量级：它的 `$D418` 只有 3637 次/秒（Giana 是
6625），但**非 `$D418` 的寄存器写很多**（4513 写/秒里 876 条是旋律、包络、滤波），
所以补填充时没有那么多"空档"可以借用。实测（30 秒窗口）：

| 参数 | wire | 传输/秒 |
|---|---|---|
| 默认（不填充） | 12% | 3707 |
| `--pad 0.12` | 13% | 9 |
| `--pad 0.15` | 22% | 16 |
| `--pad 0.2` | 47% | 35 |
| `--pad 0.25` | 58% | 42 |
| `--pad 0.3` | 60% | 44 |

注意 `--pad 0.2` 以上 wire 跳得很快——说明 0.15 附近是这首的"性价比拐点"。

推荐的起手式：

```powershell
# 1. 先确认填充本身没问题（wire 应当 <= 25%）
.\build\sidtest.exe sidplay "sidvgm\rsid\turboutrun\turboutrun_s01.sidvgm" --pad 0.15

# 2. 如果还有断音，先加领先量，不要动 pad
.\build\sidtest.exe sidplay "...turboutrun_s01.sidvgm" --pad 0.15 --pad-lead 50

# 3. 如果延迟还是明显，把块和领先一起收
.\build\sidtest.exe sidplay "...turboutrun_s01.sidvgm" --pad 0.15 --pad-lead 10 --pad-chunk 1

# 4. 如果 wire 顶到 80% 以上还在断，说明填充挤占了爆发，降 duty
.\build\sidtest.exe sidplay "...turboutrun_s01.sidvgm" --pad 0.2 --pad-duty 50
```

**断音的两个原因要区分开**：

- `wire` 低但仍然断 → 欠载，主机来不及喂。**加 `--pad-lead`**。
- `wire` 高（>80%）且断 → 填充把爆发挤掉，队列里全是 NOP。**降 `--pad` 或 `--pad-duty`**。

### 3.3 写入协议 `--proto`

| 值 | 线上字节 | 说明 |
|---|---|---|
| `1step`（播放默认） | `[slot,0x00,addr,data]` 一条 Path A | 这套接线实测最稳 |
| `2step` | `[slot,0x80,addr]` + `[slot,0x81,data]` | 旧的四芯片接线用这个 |

```powershell
.\build\sidtest.exe sidplay sid\Golden_Axe.sid --proto 1step
```

### 3.4 切窗口不再卡

播放时会自动做两件事，不需要参数：

- 播放线程请求 MMCSS 的 "Pro Audio" 特性，失败则退到 `THREAD_PRIORITY_HIGHEST`；
- 进程退出 Windows 的电源节流（EcoQoS），并且整个播放期间保持 1 ms 计时精度。

以前把窗口切到后台、或者前台有重活时 SPFM 会顿，就是这两项没做。

## 4. 整个目录连播

```powershell
.\build\sidtest.exe sidlist sid
.\build\sidtest.exe sidlist sid --from 5          # 从第 6 个文件开始
.\build\sidtest.exe sidlist sid --seconds 30       # 每首 30 秒就换
```

`sidlist` 会**递归**扫目录（含 `rsid\` 等子目录），按名字排序，每首播到你按键。

**带多个子曲的曲目会变成一个文件夹**，子曲是里面的独立文件：

```
sidvgm/Golden_Axe/Golden_Axe_s01.sidvgm   ← 23 个，一个子曲一个文件
sidvgm/Golden_Axe/Golden_Axe_s02.sidvgm
sidvgm/atmos.sidvgm                       ← 只有一个子曲的还是一层文件
```

所以 `.sidvgm` 的按键语义和 `.sid` 完全一样：

| 键 | `.sid` | 多子曲的 `.sidvgm` 文件夹 |
|---|---|---|
| `n` | 下一首曲子 | 下一个曲子（整个文件夹跳过） |
| `b` | 上一首曲子 | 上一首曲子 |
| `,` / `.` | 上一个 / 下一个子曲 | 文件夹里的上一个 / 下一个文件 |
| `q` | 退出 | 退出 |

表头会打印当前的写入协议、定时器、发送粒度。列表里子目录的文件显示为相对路径，
比如 `rsid/Ambient.sid`；也可以只给某个子目录：`sidlist sid\rsid\ganasis`。

## 4.1 播放预渲染的 `.sidvgm`

`sidextract` 可以把 `.sid` 录成 `.sidvgm`（项目自己的 VGM 形容器），
`sidplay` 直接按里面的时间线回放，不再跑 6502：

```powershell
# 录 60 秒（默认引擎 libsidplayfp，digi 鼓和真 RSID 都不丢）
.\build\sidextract.exe sid\Golden_Axe.sid out.sidvgm --seconds 60

# 回放
.\build\sidtest.exe sidplay out.sidvgm

# 目录连播：sidlist 现在也扫 .sidvgm / .sidreg
.\build\sidtest.exe sidlist sidvgm
```

和 `.sidreg` 的区别：`.sidvgm` 是二进制、带时钟/PAL-NTSC/标题（GD3），
时间单位是整 tick（1/44100 s），所以可以精确复原；`.sidreg` 是纯文本，
毫秒列是浮点，适合人看和 diff。

一次转完整个 `sid\` 目录（输出到 `sidvgm\`，保留 `rsid\` 子目录）：

```bash
./tools/convert_all_sidvgm.sh --seconds 60
```

`sidvgm\` 和 `sid\` 是两套东西：`sid\` 是原始 `.sid`（6502 代码，播放时要跑），
`sidvgm\` 是同一批曲子的寄存器流（直接回放）。两边目录结构一致，
`sidvgm\` 已被 `.gitignore` 排除（内容和 `sid\` 一样是有版权的曲子）。

2SID / 3SID 曲目会被跳过——容器只装一个 SID 槽，录下来会串成一片。
当前 `sid\` 里有两首（`Anthrox_2SID`、`Hokuto_Stereo_2SID`）。

## 5. 只看不播：信息与抽取

```powershell
# 只读头部
.\build\sidtest.exe sidinfo sid\Golden_Axe.sid

# 抽出寄存器流（纯文本，不需要硬件）
.\build\sidtest.exe sidextract sid\Golden_Axe.sid out.sidreg --seconds 120

# 把已经渲染好的流播出去（不再跑 6502）
.\build\sidtest.exe sidplay out.sidreg
```

`.sidreg` 每行是 `时间(ms) 寄存器 值`，可以直接用编辑器改，也能和别的
工具的输出做 diff。它和 `.sid` 的区别：`.sid` 是活的（无限播、随时可能
按键中断），`.sidreg` 是一段固定长度的录音，播完就结束。

## 6. 不接硬件做验证

加 `--dry-run` 就完全不碰 USB，只把要发的字节攒下来并统计：

```powershell
.\build\sidtest.exe --dry-run sidplay sid\Golden_Axe.sid --seconds 2
#   dry-run: 2330 events -> 9420 bytes
```

这个模式适合确认"某首歌是否被正确解析"——事件数和字节数对得上，硬件
那边就不用试了。

## 7. 参数速查

| 参数 | 默认 | 说明 |
|---|---|---|
| `--slot N` | 3 | SPFM 槽位 0..3 |
| `--device N` | 0 | FTDI 设备序号 |
| `--proto 1step\|2step` | `1step` | 寄存器写协议 |
| `--timer hprec\|hybrid\|mmtimer\|vgmplay` | `hprec` | 等待原语 |
| `--flush register\|command` | `command` | USB 发送粒度 |
| `--flush-gap MS` | 关（旧规则 0.09 ms） | 一批至少攒够 MS 才发；digi 曲目用它压传输次数 |
| `--pad MS` | 关 | 反向方案：用 NOP 字节把 ≤MS 的间隔填到线上，由 UART 时钟计时 |
| `--pad-duty PCT` | 75 | `--pad` 允许占用的线速百分比 |
| `--pad-lead MS` | 25 | 主机领先音乐的上限 = 延迟 + 欠载余量 |
| `--pad-chunk KB` | 2 | 每次 flush 的块大小 |
| `--pad-burst MS` | 200 | 漏桶能攒的填充预算 |
| `--pad-scope all\|digi` | all | 只填与 `$D418` 相邻的间隔（避免动旋律） |
| `--pad-min MS` | 0 | 短于这个的间隔不填 |
| `--pad-lag MS` | 0 | 线上时间领先音乐超过此值时暂停填充 |
| `--pad-window MS` | 0 | 局部滑动窗口，用来给填充加"就地"上限 |
| `--pad-local PCT` | 100 | 该窗口内允许占用的线速上限 |
| `--pad-partial` | 关 | 允许填一半（默认全填或全不填，避免变速感） |
| `--digi HZ` | 0（关） | 只对 `$D418` 数字鼓按 1/HZ 重采样；旋律/门控/ADSR 不动 |
| `--dedup-vol` | 关（`--pad` 自动开） | 丢掉与当前锁存值相同的 `$D418` 写 |
| `--seconds N` | 0（无限） | 播放时长；给了就变成先渲染再回放 |
| `--subsong N` | 头部默认 | 子曲序号，0 起 |
| `--speed X` | 1.0 | 倍速 |
| `--no-cache` | 关 | 不使用 `sid_cache\` |
| `--cache-dir DIR` | `sid_cache` | 缓存目录 |
| `--raw-filter` | 关 | 丢掉曲子的滤波器编程（0x15/0x16/0x17），0x18 只清滤波位、保留音量 |
| `--dry-run` | 关 | 不发 USB |
| `--verbose` | 关 | 每次寄存器写打一行 |

`--timer` / `--flush` / `--proto` 放在命令名前后都行：
`.\build\sidtest.exe --timer hybrid sidplay x.sid` 和
`.\build\sidtest.exe sidplay x.sid --timer hybrid` 等价。

## 8. 出问题怎么定位

| 现象 | 先看什么 |
|---|---|
| `no FTDI device found` | `build\ftd2xx64.dll` 在不在；`list` 命令能不能枚举 |
| 声音在，音高全错 | 换 `--proto 2step` 试；那是 374 的地址锁存相位问题 |
| 有节奏但音少 | `--flush register` 对照，判断是不是批量发送被硬件吃掉 |
| digi 曲子发闷、像被降采样 | 看结束那行 `link:` 的 transfers/s；超过 1000 就加 `--flush-gap 2` 再听 |
| 切窗口就顿 | 确认是这一版（`--timer hprec` 默认），看屏幕上 `lag` 是否突然涨到几十 ms |
| 播放中途停 | `--seconds N` 是不是被加上了；没加就是无限播 |
