# SPFM 链路预算 vs RSID 曲目：要不要降速？

问题：RSID 那类带 CIA/VIC 中断、带数字鼓的曲目，寄存器写入密度高得多，
**按原速率推给真芯片会不会把 SPFM 链路挤爆、需不需要降采样？**

结论先说：**不需要。最重的曲子平均只用掉链路的 17.9%，最忙的一帧 38%。**
余量 4–5 倍，问题不在这里。

## 1. 链路容量（这是天花板，不能拿波特率当答案）

已实测的几何参数（`src/spfm_transport.c`：1.5 Mbaud、8N1、4 KiB USB 分包、
2 ms latency timer）：

| 量 | 值 |
|---|---|
| 线速 | 1.5 Mbaud / **10 bit per byte**（1 start + 8 data + 1 stop）= **150000 B/s** |
| 数据吞吐 | **37.5 kB/s**（每条 Path A 命令占 4 个线字节） |
| Path A 单条命令 | 4 B / 150000 = **26.67 µs** |
| 理论命令率 | **37500 条/s** |

`--proto 2step`（Path B，3 字节 + 额外一条）= 53.3 µs/条，命令率减半。

**每次 flush 都要付 2 ms latency timer**，所以可持续速率是
`batch / (wire + 2 ms)`：

| 每次 flush 的命令数 | 批量 | 持续命令率 | 占 37500 |
|---|---|---|---|
| 1 | 4 B | 493/s | 1.3% |
| 64 | 256 B | 17266/s | 46% |
| **256（V0 形状）** | **1024 B** | **29003/s** | **77%** |
| 750 | 3000 B | 34091/s | 91% |
| **1024（V1 切片）** | **4096 B** | **34941/s** | **93%** |
| 4096 | 16 KiB | 36826/s | 98% |

这也是为什么 `sidplay` 是**每帧一次 flush**（一个 C64 play routine 在一帧里
把该写的都写完）：帧长 19.96 ms，支付一次 2 ms，剩 17.96 ms 可以传 2694 字节
= **673 条命令**。这是"一帧内发完一帧的量"的真实预算。

## 2. 实测需求：116 首（每首 20 秒，`--engine lsfp`）

按 19.96 ms 一帧统计每帧命令数：

| 曲目 | 平均命令/s | 最忙一帧 | 占帧预算 673 | 一帧总耗时含 2 ms |
|---|---|---|---|---|
| Arkanoid（RSID） | 2131 | **211** | 31% | 38% |
| turboutrun | 4526 | 184 | 27% | 35% |
| Echofied_6581（RSID） | 5948 | 178 | 26% | 34% |
| Great_Giana_Sisters-rsid | 5853 | 170 | 25% | 33% |
| Echoes（RSID） | 6726 | 159 | 24% | 31% |
| stsid | 4811 | 106 | 16% | 24% |
| Wizball | 1994 | 98 | 15% | 23% |
| R-Type | 684 | 81 | 12% | 21% |

- **116 首里没有一首任何一帧超过 673 条**（超预算帧数 = 0）。
- 最重的平均需求是 Echoes 的 **6726 条/s = 链路的 17.9%**。
- 最忙的单帧是 Arkanoid 211 条：wire 5.6 ms + 2 ms = 7.6 ms，占一帧 38%。

所以"USB 被挤爆"不成立，**不需要降采样**。

## 3. 队列滞后仿真

按 FIFO 模拟（每条占线 26.67 µs），排除开头 init 爆发后的稳态滞后：

| 曲目 | 1step 滞后 | 2step 滞后 |
|---|---|---|
| Arkanoid | 0.15 ms | 0.97 ms |
| Echoes | 0.07 ms | 0.42 ms |
| turboutrun | 0.15 ms | 0.43 ms |
| Wizball | 0.15 ms | 0.36 ms |
| stsid | 0.17 ms | 1.25 ms |
| Great_Giana_Sisters-rsid | 0.12 ms | 0.37 ms |

一帧 19.96 ms，1step 的 0.15 ms 是 **0.75% 一帧**。2step 会放大到 3–4 倍
（0.4–1.25 ms），仍然可听范围之外，但没有理由换。

确实存在 1 ms 窗口内超容量的瞬间（Arkanoid 81 条 vs 容量 37.5 条、
Wizball 75 条），但持续不到 1 ms，被随后的空闲抹平——峰值滞后仍 < 0.2 ms。

## 4. 那要降速的到底是什么

不是链路，是**内容**。对比旧引擎（手写 fake6502）和新引擎（libsidplayfp）
录同一首 20 秒：

| 曲目 | 旧引擎 D418 | 新引擎 D418 | 旧写入总数 | 新写入总数 |
|---|---|---|---|---|
| Echoes | **0** | 98035 | 16212 | 129161 |
| turboutrun | **1** | 72009 | 17128 | 88847 |
| Arkanoid | **2** | 30454 | 10225 | 39957 |
| stsid | 1001 | 4011 | 24028 | 96221 |
| Wizball | 1254 | 5012 | 7775 | 39871 |

旧引擎每帧只调一次 play，帧内的 `$D418` 采样被整帧吞掉。所以旧文件小
（1/13），是因为**里面没有鼓**。新引擎把这些补回来，链路依然吃得下。

体积代价见 [RSID判定与体积对比.md](RSID判定与体积对比.md)：常规曲子 1.45×，
digi 曲 6–22×。

## 5. 真正需要处理的两件事（都不在此次的链路问题上）

1. **硬件播放器 `sidtest.exe` 还在用旧核心**（`src/sid_rsid.c` 的 fake6502），
   它链不到 libsidplayfp。所以即便链路有余量，硬件上现在听不到 digi 鼓。
2. 旧核心处理 `play=0` 的方式是**猜入口**（读 `$FFFE` / `$0314`），不是真的模拟
   CIA/VIC 中断；`sid_stream_next_frame()` 无条件每帧 `call_play` 一次。所以
   CIA 100 Hz 的曲子（stsid）在硬件上只跑 50 Hz，音符少一半。这条与速率无关，
   是模型缺失。

## 6. 如果哪天真的要限流

现成的 `--limit HZ` 是按"固定时间基 + 丢弃重复值"做的，不是简单抽样。
历史实测（60 秒窗口，slot 量化 + 等值丢弃）：

| `--limit` | Giana 保住的 `$D418` 变化 | Outrun 保住的 |
|---|---|---|
| 8000 | **100%** | **99.99%** |
| 6000 | 91% | 95% |
| 4000 | 69% | 79% |
| 2000 | 40% | 47% |

**8000 Hz 对这两首是无损的**（只删掉"重写当前值"的冗余），还能把 Giana 的总
命令数砍掉 64%。所以真需要留余量时，优先用 `--limit 8000`，不要往下压到
7000 以下（那才是真正的降采样，会毁鼓的音色）。

## 复现

```powershell
# 全量录制（116 首 × 20 秒）
foreach ($f in Get-ChildItem sid\*.sid, sid\rsid\*.sid) {
    .\build\sidextract.exe $f.FullName "tmp\$($f.BaseName).sidvgm" --seconds 20
}
```

分析脚本按 19.96 ms 分帧统计每帧命令数，对比 673 条的预算；
容量侧用 `batch / (batch/150000 + 0.002)` 计算可持续命令率。
