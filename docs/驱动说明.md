# SID 6581 驱动说明

## 1. 文件

| 文件 | 作用 |
|---|---|
| `src/spfm_transport.c/h` | SPFM 字节流传输层（FTDI 打开、缓冲、flush、路径 A/B、dry-run 抓包、高精度时钟） |

## 2. 一次寄存器写到底发生了什么

主机侧（驱动层）只发 4 字节：

```
[slot, 0x00, addr & 0x1F, data]
```

固件路径 A 展开成两次 BusWrite。当前硬件是
**74LS374 + 74HCT02 + 74HCT32**（见 [接线表_374_02_min.md](接线表_374_02_min.md)）：

| 步 | 总线 | 74LS374 | 74HCT32 | SID |
|---|---|---|---|---|
| 1 | A0=0, D=`addr&0x1F`, /WR 脉冲 | `LE = NOR(0,/WR 低) = 1`，`/WR` 下降沿捕获地址 | `TRIG_n = ¬A0∨/WR∨CSn = 1` | `/CS=1`，**未选中**，忽略总线 |
| 2 | A0=1, D=`data`, /WR 脉冲 | `LE = 0`，保持上次地址 | `TRIG_n = 0` | `/CS=0` 且 `R/W=0`（`R/W` 直接接 `/WR`），写入 |

关键点：

- **地址相绝不会误写**：`A0=0` 使 `TRIG_n` 恒为 1，SID 的 `/CS` 恒高，根本不看总线。
  直接把 `CSn` 接到 SID 的 `/CS` 就会在地址相也写一次，写 `0x04` 时把 gate 清掉，
  表现为每次改频率都重启包络（咔哒声）。
- **`TRIG_n` 只接 `/CS` 一个负载，`R/W` 由 SPFM 的 `/WR` 直接驱动。**
  早期版本把 `TRIG_n` 同时接两个脚、中间还串了一级 74HC74。2026-11-20 实测拆掉 74HC74、
  把两条线分开后，单次写入反而更稳。原因是一个 74HCT32 门带两个 CMOS 负载会拖慢边沿，
  那才是当时“失真”的真正原因。
- **SID 在这里就是异步写器件**：`/CS` 与 `R/W` 同时为低就锁存。之前从 reDIP-SID 的 RTL
  推出“必须跨 PHI2 上升沿”是过于保守的结论，`/WR` 自身的宽度就够。
- **`PHI2`（SID pin8）由独立 1 MHz 晶振供给**，与总线时序无关。它不参与写使能，
  但必须存在——没有时钟就没有内部振荡器与包络。

## 3. 三种写模式

`--write-mode` 选择，默认 `two-phase`；`.sid` 播放走 `--proto`，默认 `1step`
（即 `path-a`，见 §6.5）。

### 3.0 为什么两相间隔基本不是问题

这一点值得先说清楚，因为它决定了要不要做时序退让。

SID 的写操作需要三件事同时/依次成立：地址稳定、`/CS` 有效、`/WR`（即 R/W）出现
低脉冲。在我们的方案里：

- **地址不是靠总线保持的，是靠 74LS374 保持的。** 地址相一结束，Q0–Q4 就锁死了，
  后面总线上的地址线随便变都不影响 SID。所以"两相之间隔多久"对地址稳定性没有意义。
- **地址相绝不会误写**：那段时间 `A0=0` 使 `TRIG_n=1`，SID 的 `/CS` 为高，根本不看总线。
  这一点和两相间隔也无关。
- **数据相是一个完整的 `/WR` 低脉冲**：固件 `BusWrite` 拉低 `/WR`、写数据、再拉高，
  低电平宽度是几十到几百纳秒量级，而 SID 只需要 `/CS` 与 `/WR` 在 PHI2 的一个周期内
  建立即可（1 MHz 下 1 µs）。远够。

换句话说：**`two-phase`（以及 `path-a`）都是安全的**，两相紧挨着发不会破坏任何东西。真正会被 USB 抖动
影响的是**不同寄存器之间**的间隔（0–125 µs），比如"写完频率到抬起 gate"之间，
而这个抖动对音符起音没有可感知影响。

既然两种都安全，就按实测挑：`sidlist sid` 整目录对比下来，`1step`（`path-a`）
能放对若干首 `2step` 放乱的曲子，所以 `.sid` 播放默认用 `1step`，还省掉三分之一
的字节。差别的来源符合异步模型：`1step` 把地址相和数据相交给固件连续发出，
两相之间不存在主机可插手的空隙；`2step` 把这段空隙留在主机侧，让 USB 调度有机会
落在两相中间。既然 SID 不需要这段空隙，把它交还给固件就是把一个抖动源去掉。

下面两种模式是排查工具，不是必需品。

### 3.1 `path-a`

4 字节，一次命令，固件内部连续发两相。

```
[slot, 0x00, addr, data]
```

推荐模式，唯一不需要主机侧时序的模式。第 4 字节还在 UART 移位寄存器里时，
固件已经开始处理前 3 个字节了，所以两相之间是"固件解析耗时"，大概几微秒。

### 3.2 `phased`

两次路径 B，中间插 NOP：

```
[slot, 0x80, addr]  [0x80 × gap]  [slot, 0x81, data]
```

总线效果和 `path-a` 完全相同，但两相间隔由 `--gap N` 控制。用途是**排除法**：

- 如果 `phased --gap 0` 和 `path-a` 表现一致（应该一致，因为总线效果相同），
  说明固件路径 A 的实现没问题；
- 如果加大 gap 之后才响，问题在固件的两相实现细节上，跟接线无关；
- 如果无论 gap 多大都不响，问题在接线或供电，不在时序。

代价是每次写多一个 3 字节命令，吞吐降到路径 A 的 2/3。

### 3.3 `phased-flush`

字节流和 `phased` 相同，但两相之间强制 `FT_Write` 一次，插入一个 USB 往返
（几十 µs 到 1 ms）。极端诊断用：如果 `phased-flush` 能响而 `path-a` 不响，
时间尺度上的差异足以定位到微秒级以内的问题。

## 4. 初始化序列

`sid_init(slot, volume)` 做的事：

1. 25 个寄存器全写 0（`0x00`–`0x18`）。374 上电后 Q 输出不定，SID 也可能被总线
   杂波写进随机值，先全清。
2. `0x18 = volume`，音量。**复位后是 0，不写就完全没声音。**
3. 三个声部写中性参数：`AD=0x09`、`SR=0xF0`、`PW=0x800`（50%）、控制寄存器 0（gate 关）。
4. `0x15/0x16 = 0x7FF`、`0x17 = 0x00`：滤波器全开、无谐振、无通道路由，
   避免初始状态把声音滤没了。

总共 44 次寄存器写，`selftest` 会校验这个数字。

## 5. 声部 API

```c
sid_note_on(slot, voice, midi_note, wave, ad, sr);
```

写顺序固定为 `freq_lo → freq_hi → AD → SR → control(wave|GATE)`。gate 必须是最后
一次写，否则包络会在频率还没落定时启动，起音音高会飘。

```c
sid_note_off(slot, voice);   // control = wave，gate 清零，走 release
sid_note_kill(slot, voice);  // control = 0，立即静音
```

`note_off` 保留波形位，所以 release 段是同一个波形；`note_kill` 把波形也清掉，
输出直接回到 DC 0，不等包络。

## 6. 频率换算

```
freq_reg = round(f_out × 16777216 / PHI2)
```

1 MHz 下 `A4 = 7382`、`C4 = 4389`、`A2 = 1845`，和 `arduino_sid/midi.c` 一致。

`tools/gen_freq.py` 按公式生成 128 项表，同时和参考表比对。参考表 `freq[]` 有两处
问题（不影响常用音域，但值得知道）：

| MIDI | 音名 | 参考表 | 正确值 | 说明 |
|---|---|---|---|---|
| 23 | B0 | 581 | 518 | 抄成了 C#1 的值，八度错 |
| 99–107 | D#7–B7 | — | — | 整体低了一个半音（99 项写的是 D7 的值） |

常用音域（MIDI 12–98）逐项误差 ≤ 1%，直接用参考表也可以，但驱动用的是公式表。

## 7. 没有硬件时怎么验证

`selftest` 完全离线，检查 30 多项：

- 每条命令都是 4 字节、slot 3、`byte1 = 0x00`、寄存器 `< 0x20`；
- 寄存器掩码 `& 0x1F` 生效（0x38 变成 0x18）；
- `init` 产生 44 次写，且有一次 `0x18 = 0x0F`；
- `note_on` 是 5 次写且顺序正确、gate 在最后一次；
- 声部 2/3 的基址是 0x07/0x0E；
- `note_off` 清 gate 但保留波形，`note_kill` 全清；
- PWM 高字节只有 4 位、滤波器截止 11 位按 3+8 拆分；
- 频率表单调且 A4/C4/A2 三个锚点正确；
- `phased` 模式产生 `[addr] NOP×gap [data]`。

`--dry-run` 则把任何子命令的字节流解码成总线动作打印出来：

```
[   0] A slot3  BusWrite(A0=0,D=0x18)  BusWrite(A0=1,D=0x0F)   => SID reg 0x18 = 0x0F
```

## 8. 上机顺序建议

1. `sidtest list` 确认 FT232R 认到。
2. `sidtest checkup` —— 按提示量 1 MHz、+5 V、+12 V，然后看 pin 27 的直流变化，
   再放三角波。这一步能一次性分辨"没供电""/CS 没门控""A4 断线"三类问题。
3. `sidtest scale` —— 三个八度的音阶，听音高是否正确（音高偏差说明 PHI2 不是 1 MHz）。
4. `sidtest chord` —— 三个声部同时响，验证声部互不干扰。
5. `sidtest music` —— 三声部小曲，用来整体听感验证：
   - 声部 1：脉冲波旋律（`SID_CTL_PULSE`，PW 0x600）
   - 声部 2：三角波低音（`SID_CTL_TRI`）
   - 声部 3：噪声打击乐（`SID_CTL_NOISE`），底鼓 / 军鼓 / 踩镲

   内置三首：`twinkle`（小星星）、`ode`（欢乐颂）、`birthday`（生日快乐）。
   速度 `--bpm`（默认 120），重复 `--loops`，`--list` 列出全部。

   实现要点：SID 的包络只在 gate 的 **0→1 边沿**重启，所以连续同音必须先把
   gate 拉低再拉高，否则两个同音会连成一个长音。`mus_note_start()` 做的就是这件事。
   打击乐的"音高"其实是噪声时钟频率：`0x0500` 低 = 底鼓隆隆声，
   `0x0C00` 中 = 军鼓，`0x2000` 高 = 踩镲嘶声；配合极短的 AD/SR 让它几十毫秒内衰减完。
5. `sidtest noise` / `pwm` / `filter` —— 逐项验证噪声、PWM、滤波器。
6. 如果前几步有异常，用 `--write-mode phased --gap 8` 复测，对比是否为时序问题。

## 5. 音乐播放的包络设计

`sidtest music` 用三个声部同时演奏，包络是让它听起来像"演奏"而不是"风琴长音"的关键。

### 5.1 钢琴式包络：Sustain = 0

SID 的 ADSR 四个数字各 0..15：

```
AD = (attack << 4) | decay
SR = (sustain << 4) | release
```

**关键在 `sustain = 0`。** Sustain 是"按住键时保持的音量"：

- `sustain = 15` → 音符在 gate 期间一直满音量，直到下一个音符 → **无限延长，风琴感**
- `sustain = 0` → 音符衰减到 0 就自己消失，gate 只是让它在 release 段收尾 → **钢琴感**

当前的取值：

| 声部 | AD | SR | 含义 |
|---|---|---|---|
| 旋律（脉冲波） | `0x08` | `0x06` | A=0 瞬起，D=8（300 ms 衰减），S=0，R=6（204 ms 释放） |
| 低音（三角波） | `0x0A` | `0x06` | D=10（1500 ms），因为低音一小节才换一次 |
| 打击乐（噪声） | 见下 | S=0 | 衰减时间决定"鼓声"的长度 |

Decay 索引对应的实际时间见 `sid_adsr_decay_ms[]`：索引 7 = 240 ms、8 = 300 ms、
9 = 750 ms、10 = 1500 ms。

### 5.2 断音：提前一拍降 gate

`sustain = 0` 只保证音符自己会衰减，但相邻同音仍可能连起来。所以播放循环里会在
音符时值结束前**一个 tick** 主动降 gate：

```c
if (mleft == 1 && sc->melody[mi].ticks) sid_note_off(g_slot, 0);
```

这样每个音符都有一个明确的 0→1 边沿（重触发包络），断句清楚。

### 5.3 打击乐

SID 的噪声通道频率寄存器控制的是**噪声时钟速率**，不是音高：

| 鼓 | 频率寄存器 | Decay | 听感 |
|---|---|---|---|
| 底鼓 | `0x0400` | 8（300 ms） | 低频隆隆 |
| 军鼓 | `0x0E00` | 7（240 ms） | 中频短促 |
| 踩镲 | `0x2400` | 5（168 ms） | 高频嘶声 |

**衰减时间不能太短。** 早先版本用 0x00（6 ms）和 0x01（24 ms），听起来像数字干扰脉冲
而不是鼓声——24 ms 比人耳能识别的鼓声短太多。现在最短的踩镲也有 168 ms。

节奏型（以 1/16 音符为 tick，8 tick 一个循环）：`t%8==0` 底鼓，`t%8==4` 军鼓，
`t%4==2` 踩镲。

### 5.4 曲目来源

| 曲子 | 来源 |
|---|---|
| twinkle / ode / birthday | 手编，C 大调，旋律 + 和弦根音低音 |
| **bach** | 移植自 `arduino_sid/Source/SID_Bach/SID_Bach.ino`（Alexis Kotlowy, 2011, Public Domain），原始音高 OFFS=36，本实现整体 +12 抬高一个八度，避免与三角波低音撞在同一音区 |

Bach 原曲的 `notes[]` 数组共 40 项（含 3 个休止），移植时保持原音符顺序，
每音 2 个 tick，总长 82 tick。

## 6. .sid 播放：从 6502 到寄存器流

### 6.1 为什么要跑一遍 6502

`.sid` 文件里没有音符，只有 6502 机器码和一个头（load / init / play 地址）。
音乐是 init 和 play 例程执行时写 `$D400–$D41F` 的**副作用**。所以现实中播放一首
`.sid` 只有一条路：

1. 用一颗 6502 仿真核心按 C64 的节奏调用 init（一次）和 play（每帧一次）；
2. 把每次寄存器写入连同"它发生在第几微秒"记下来；
3. 在真硬件上按同样的时间间隔把这些写入推出去。

第 1、2 步是 `src/sid_rsid.c`，第 3 步是 `src/sidplay.c`。

仿真核心（fake6502 + VIC raster + CIA timer A/B）来自 STC32G 芯音乐工程
（`usb_ctest/tools/sid_extract.c`），原样搬过来只改了接口和状态复位，这样两个工程
对同一首 `.sid` 的还原结果一致，可以互相校对。**没有重写。** 原先的 Python 版
（py65）每首几分钟，现在 30 秒的音乐 30 毫秒跑完。

### 6.2 事件流格式

```text
<time_ms> <reg_hex> <val_hex>
0.0000 04 08
0.0000 0b 08
19.9868 18 0f
```

- `time_ms` 从 init 例程**执行完**算起。init 期间的所有写入统一钉在 t=0，因为它们在
  第一帧 play 之前必须全部生效，而 SID 分辨不出这些写入之间的间隔。
  （早先版本用 CPU 周期做时间戳，R-Type 的 init 跑了 9 ms，结果那 28 条初始化写入
  排在第一帧之后——声音会先响一下再被覆盖。）
- play 期间的写入用 `帧号 × 每帧周期 + 帧内周期` 换算，保留亚帧精度，
  RSID 的 PCM/digi 采样靠的是帧内密集写 `$D418`，精度丢了就变成噪音。

### 6.3 定时：为什么必须用绝对 deadline

一台 C64 的 PAL 帧是 19.96 ms，一帧最多写 ~50 个寄存器。回放有两种写法：

| 写法 | 结果 |
|---|---|
| 每个事件 `sleep(t[i+1]-t[i])` | 每次调度的误差累加，几分钟后整首歌被推到一帧甚至几帧之后 |
| 记一个起点，等 `起点+t[i]`（本实现） | 误差有界，不会漂 |

`src/spfm_transport.c` 提供两个函数：

- `spfm_now_us()` — QPC / `CLOCK_MONOTONIC` 的单调微秒时钟，整数运算，长曲子不漂。
- `spfm_wait_until_us(deadline)` — 混合等待：离 deadline 还有 >1.5 ms 就 `Sleep()`
  大部分，最后 1 ms 忙等。`spfm_open()` 里调用 `timeBeginPeriod(1)` 把 Windows
  调度粒度从 15.6 ms 降到 1 ms，否则 `Sleep(4)` 可能真的阻塞 15.6 ms——等于一帧。

这和参考播放器 `Denjhang_Music_Player` 的 `sleep_hybrid_us()`
（`ym2608_window.cpp`）是同一个做法。实测 10 秒 R-Type 最大滞后 **2 ms**，
一帧是 19.96 ms，听众听不出；改之前不升 timer resolution 时是 14 ms。

### 6.4 每帧一次 flush，不是每次写都 flush

一帧 50 个写入，如果每个写入都单独跑一次 USB 传输，FTDI 的 2 ms latency timer
会把 ~100 ms 的周转塞进 20 ms 的帧里，音乐立刻散架。所以
`sid_set_deferred_flush(true)` 让 `sid_write()` 只进缓冲区，由播放器在
"下一帧还没到"的空档里 flush 一次。字节顺序不变，SID 看到的写序列和原曲完全一致，
USB 传输次数少 50 倍。

这一条对 `1step` 和 `2step` 都成立：两种协议在播放时都只在帧边界 flush。
（早先 `SID_WRITE_BURST` 分支漏了 flush，字节会一直躺在 64 KiB 缓冲里，
表现为"一步写入完全没声"。已修。）

### 6.5 写入协议：`--proto 1step | 2step`

`--proto` 决定一次寄存器写变成几段总线动作：

| 协议 | 出去的字节 | 含义 |
|---|---|---|
| `2step` | `[slot,0x80,addr]` + `[slot,0x81,data]` | 两次 Path B，地址相和数据相分开，中间的空隙由主机控制 |
| `1step` | `[slot,0x00,addr,data]` | 一次 Path A，固件自己连发两个总线周期 |

样例（R-Type 前 1 秒，1177 条写入）：`1step` 4808 字节，`2step` 7212 字节，
一步写入少三分之一。

**播放默认是 `1step`。** 实测 `sidlist sid` 跑完整目录，`1step` 让若干首
`2step` 放得乱七八糟的曲子恢复正常，说明这颗 SID 在这套接线下是异步写器件：
`TRIG_n` 直接驱 `/CS`、`/WR` 直接驱 `R/W`，两个都为低就锁存，主机去控制两相之间
的空隙没有任何好处，反而给了 USB 调度干扰它的机会。`2step` 保留一个参数就能切回，
因为它是旧接线下唯一能工作的方式。

`--write-mode` 仍然可用，是给探针用的（`split` 分辨是哪一相丢周期、
`path-a-soft` 隔离 USB 节奏、`two-phase-nop` 用固件 NOP 填缝）。命令行显式给了
`--proto` 或 `--write-mode` 时，播放器不会用默认值覆盖它。

### 6.5 缓存

一次提取 = 60 秒音乐约 30 ms CPU，所以缓存不是必需的，但播放列表连着翻曲子时有用。
`sid_cache/<名字>_s<子曲>_d<秒>.sidreg`，格式和 STC32G 工程通用，可以互相拷。
`--no-cache` 跳过读写。

| 命令 | 作用 |
|---|---|
| `sidinfo <f.sid>` | 只读头：标题、作者、PAL/NTSC、子曲数量 |
| `sidextract <f.sid> <out.sidreg> [--seconds N] [--subsong N]` | 渲染成文本流，不需要硬件 |

### 6.7 已覆盖的文件

`sid/` 下 6 首 + `sid/rsid/` 下 93 首，共 99 个全部提取成功，时间戳单调递增
（有 3 个文件需要 `$0314` 回退，见下）。

**`play_addr = 0` 不是错误。** 这样的文件有两种可能：

| 类型 | 每帧音乐代码的位置 |
|---|---|
| RSID | init 把 handler 装到硬件 IRQ 向量 `$FFFE` |
| PSID | init 把 handler 装到 KERNAL 软 IRQ 向量 `$0314` |

头里没有字段区分，所以两个都试；低于 `$0100` 的地址在零页，不可能是代码，
等同于"没设"。`sid/rsid/F1_Simulator.sid`、`Flimbos_Quest.sid`、`lazy.sid` 属于
PSID 这种情况，只看 `$FFFE` 会得到 21 条写入就结束。

### 6.8 digi 鼓声：为什么 Giana Sisters 的鼓不响（2026-11-20）

`sid/Great_Giana_Sisters-rsid.sid` 文件名带 `-rsid`，但头是 **PSID v2**。它的鼓声
是 C64 上最典型的"音量寄存器 digi"：**CIA2 timer A 触发 NMI，NMI 处理程序每次
往 `$D418` 写一个 4 bit 采样值**。所以鼓的采样率是 CIA 定的几 kHz～几十 kHz，
和 50 Hz 的视频帧完全无关。

从文件里挖出来的证据（`$70F0` 起，用 `sidextract` 抽 30 秒只有 1 条 `$D418`，
所以这不是参数问题）：

```text
init:  A9 19       LDA #$19
       8D 18 03    STA $0318      ; NMI 向量低字节
       A9 9B       LDA #$9B
       8D 19 03    STA $0319      ; NMI 向量高字节 -> $9B19
       ...
       8D 04 DD    STA $DD04      ; CIA2 timer A latch lo  (采样率)
       8D 05 DD    STA $DD05      ; CIA2 timer A latch hi
       8D 0E DD    STA $DD0E      ; 启动 CIA2 timer A

NMI($9B19):  48           PHA
             A5 04 / C5 02  LDA $04 / CMP $02   ; 采样指针到头？
             B1 03         LDA ($03),Y        ; 取一个字节
             29 0F         AND #$0F
             4A            LSR A
             18 69 13      CLC / ADC #$13     ; 合成 $13..$1A
             8D 18 D4      STA $D418          ; ← 鼓声就是这个
             A9 18 8D 18 D4  STA $D418         ; 高半字节样本
             AD 0D DD      LDA $DD0D          ; 清 CIA2 ICR
             68 40         PLA / RTI
```

采样率表在 `$AF80` / `$AF40`（8 个子曲各一项），节奏表在 `$BF00`。

**我们这边一行都跑不到**，因为仿真核心缺三样东西：

| 缺失 | 后果 |
|---|---|
| `$DD00-$DD0F`（CIA2） | `STA $DD0E` 被当成普通 RAM 丢掉，timer 永远不启动，NMI 永远不来 |
| NMI（`$0318/$0319`） | `$9B19` 那段代码从不执行，所以 `$D418` 一句都不写 |
| `check_hardware_irq()` 的调用 | 函数写好了但**没有任何地方调它**，`vicClock()` / `ciaClock()` 是死代码；连 IRQ 都没真的注入过 |

**已修复（2026-11-20），改动都在 `src/sid_rsid.c`：**

| 改动 | 说明 |
|---|---|
| `cia_t` 结构体 + 两份实例 | CIA1 = `$DC00`、CIA2 = `$DD00`，同一套读写函数；CIA1 的 ICR bit7 拉 `/IRQ`、CIA2 的拉 `/NMI` |
| NMI 注入 | `$0318/$0319`（退到 `$FFFA/$FFFB`），响应 7 周期，指令边界上取，优先级高于 IRQ |
| IRQ 注入 | `$FFFE` 退回 `$0314`（原来 `get_play_addr` 有回退，但 `irq6502()` 从没被调用过） |
| `run_machine()` 按周期推进 | 每个 tick 精确跑 `play_cycles` 个周期；play 例程 RTS 之后 CPU 停在 `IDLE_PC`，时钟照样走，NMI 照样触发 |
| 6502 周期表 | 256 项 `op_cycles[]` + 已取分支 +1 / 翻页 +1，`clockticks6502` 现在真的等于 CPU 周期 |
| `cia_period()` | 6526 是 `latch + 1` 个周期一次下溢，**latch = 0 表示 65536 而不是 1** |

最后一条踩得很实在：一开始按 `latch + 1` 算，Giana 的标题曲 `latchA = 0`，结果变成
每周期一次 NMI 风暴（4 秒 561000 次），play 例程完全被饿死、0 条寄存器写入。改成
`latch = 0 → 65536` 之后立刻正常。

**实测结果（`sid/Great_Giana_Sisters-rsid.sid`，子曲 0）：**

| | 修复前 | 修复后 |
|---|---|---|
| NMI 次数 / 4 s | 0 | 6829 |
| `$D418` 写入 / 20 s | 1 | 108616（≈6785 条/秒） |
| 总寄存器写入 / 20 s | ~9000 | 117543 |
| `$D418` 取值 | 只有 `07` | `13`–`1A` 共 8 档，正是 4 bit 采样 |
| 抽取 20 秒耗时 | — | 0.6 s |

99 个文件回归：全部有写入、时间戳单调，无回归。`SIDR_DEBUG=1` 会打印向量、
两个 CIA 的 latch/ctrl、以及 NMI/IRQ 实际响应次数。

### 6.8.1 两种模型：PSID（默认）与 RSID（`--rsid`）

上面那套完整时钟 + 中断**默认关闭**，因为它的写入密度远超 SPFM 链路能实时运送的量：

| 模型 | 每个 tick 干什么 | 典型写入量 | 怎么开 |
|---|---|---|---|
| **PSID（默认）** | 调一次 play，返回就结束；时钟不推进、不响应中断 | 20 ms 一帧约 50 条 | 不用管，默认就是 |
| **RSID** | 整个 tick 一直跑机器，指令边界上响应 NMI/IRQ | Giana 鼓 ≈6785 条/秒 | `--rsid` |

`--rsid` 在 `sidplay`、`sidlist`、`sidextract` 上都有；启动行会打印
`..., PSID model` 或 `..., RSID model`。

**PSID 模型的输出和引入 digi 支持之前逐字节一致**，这一点是硬性要求：digi 那轮改动
曾经把默认路径也切到"按周期推进"，后果是很多普通曲子的音量寄存器被搞坏——
原因是原来的 `call_play()` 没有周期预算（play 例程可以随便跑超过一帧的周期），
而 `run_machine()` 按帧周期截断，play 中途被打断。被打断的如果正好是写 `$D418`
的那一段，芯片就停在之前那个音量值上，听感就是"音量不再变化"。

所以现在的拆分是：

- `call_play_psid()`：无周期预算（守卫 100 万条指令，实际永远碰不到），
  只累加`已取分支 +1 / 翻页 +2`到 `clockticks6502` —— 这正是原版的帧内时间戳口径。
- `call_play()` → `run_machine()`：精确跑 `play_cycles` 个周期，只在 `--rsid` 下用。

回归验收方式：对 `sid/` 表层 12 个文件，默认模型下 `sidextract` 的输出（含时间戳）
与上一版 `0011fde` 逐字节相同；`--rsid` 下 Giana 的 `$D418` 仍然是 ≈6821 条/5 秒。

参考项目 `SIDPod-master/src/audio/C64.cpp` 提供了一条有用的规则——`useCIA()`：
`speed` 字的第 N 位决定子曲 N 是否 CIA 定时，定速用 init 留下的 `$DC04/05`
latch。这条已经照搬（见 §6.9）。但 SIDPod 自己**也没有 NMI 和 CIA2**，所以它放
这个文件同样没有鼓，不能拿它当正确答案对照。

### 6.9 play 速率（仅 `--rsid` 生效）

原来无论 speed 字说什么，一律按 50.125 Hz 调 `play()`。现在：

- `subsong_uses_cia()` 读 `speed` 的第 N 位；
- 是 CIA 定时就用 init 之后 `$DC04/05` 的 latch 值当每 tick 的周期数
  （`pick_play_cycles()`），否则用帧周期；
- `sid_stream_frame_ms()` 返回真实 tick 时长，播放器的绝对 deadline 调度跟着变；
- `sidextract` 会打印 `play rate: xx.x Hz (CIA timer A | video frame, N cycles)`；
- `sid_song_info_t` 新增 `cia_timed` / `play_cycles` / `play_hz` 三个字段。

**默认的 PSID 模型不看 speed 字**，一律按视频帧（19.96 ms / 16.67 ms），
`cia_timed` 报 0。这是刻意的：PSID 模型不跑中断，就算把 tick 缩到 CIA 的周期，
NMI 也不会来，缩了只会让同一段 play 被反复调用。CIA 定速只在 `--rsid` 下有意义。

`speed` 字的分布（99 个文件）：117 个 `0x00000000`（全帧同步）、3 个
`0x00000001`、一个 `0x000007FF`、一个 `0x000001FF`、一个 `0x0000001F`。

### 6.10 `--limit`：把 `$D418` 的更新率钉住（2026-11-20）

`--rsid` 让 digi 鼓声出来了，但它同时把 `$D418` 的写入率一起带了上来：
Giana Sisters 原样跑 20 秒是 108616 条 `$D418`，最密的 100 ms 里有 680 条。
这些写入不是"数据量太大"，而是**更新率**不受控——链路能不能跟上，取决于
2 ms 的 USB latency timer、固件把每条命令翻成两个总线周期的速度、以及队列里
已经堆了多少。堆满了就是丢包，听感是鼓声断续，而不是整齐的降采样。

`--limit HZ` 把这件事变成一个可以自己选的数：

```bash
sidtest.exe sidplay sid/Great_Giana_Sisters-rsid.sid --rsid --limit 200
build\sidextract.exe sid/Great_Giana_Sisters-rsid.sid out.sidreg --rsid --limit 200
```

**实现方式（生成侧）**：`sid_rsid.c` 的 `on_sid_write()` 在捕获阶段处理，
只针对寄存器 `0x18`。

1. 把每次写入的 CPU 周期映射到固定的时间格 `1/HZ` 秒（时基由 CPU 时钟算出，
   和 MDPlayer `dacControl` 的 "固定采样率 + 只发走在播放头前面的样本" 同构）；
2. 同一格里后来的写入**就地覆盖**前一格留下的那条事件——这是采样保持，
   窗口关上时芯片停在最后那个值；
3. 和当前保持值相同的写入直接丢弃（芯片本来就停在那儿，写一次是白费）；
4. 时间戳量化到格的起点，但**不允许倒退**，保证整条流仍然单调有序。

其它 24 个寄存器**一条都不动**，时间戳原样保留，所以音符、gate、ADSR 完全不受影响。
这是刻意的取舍：digi 的损失只落在音量上，旋律一点都不能碰。

**实现方式（链路侧）**：`spfm_transport.c` 新增 `spfm_tx_pending()` /
`spfm_flush_drain()`，播放器在原来每帧 flush 的位置改成 `flush_paced()`：
推完这一批就问一次 FTDI 驱动还有多少字节排在发送队列里，超过低水位就等它出去，
但有 deadline，不会为了让队列排空而错过下一个事件。这就是 MDPlayer
`SendData()` + `while(!IsBufferEmpty())` 的对应物。只有开了 `--limit` 才走这条路，
默认 PSID 播放一个字节一个字节都没变。

**实测（Giana Sisters，20 秒，PAL）**：

| 设置 | `$D418` 条数 | 最密 100 ms | 折算峰值 |
|---|---|---|---|
| 不限（纯 `--rsid`） | 108616 | 680 | ≈6800/s |
| `--limit 6000` | 29877 | 508 | ≈5100/s |
| `--limit 4000` | 22653 | 370 | ≈3700/s |
| `--limit 2000` | 13236 | 200 | ≈2000/s |
| `--limit 1000` | 7463 | 101 | ≈1000/s |
| `--limit 200` | 1705 | 21 | ≈210/s |

峰值基本就是 HZ 本身，说明限速按预期生效。`--limit 200` 只保留 1705 条而不是
4000 条（200×20），少的那些是**重复值**——鼓的空档里 `$D418` 一直写 `0x18`，
第三次那步把它们全滤掉了。留下的值分布仍然是 digi 的 8 个电平
（`07 13 14 15 16 17 18 19 1a`），没有变成两三个。

`sidextract` 会打印保留率：

```
  $D418   : limited to 200 Hz - 1705 of 108616 samples kept (85/s, was 5435/s)
```

**关于带宽的一个诚实说明**：不限速时峰值约 30 kB/s，1.5 Mbaud 8N1 是 187.5 kB/s，
只占 16%。所以 `--limit` 不是为了"塞得下"，而是为了把更新率从曲子的密度里拿出来，
交给自己定；链路侧排空检查的作用是让"跟不上"变成一个可见的数字（播放行尾的
`tx N B starved M`），而不是悄无声息地丢样本。

**回归**：默认（PSID）模型下，`sid/` 表层 12 个文件的 `sidextract` 输出与上一版
逐字节相同；`--rsid` 不加 `--limit` 时与上一版也逐字节相同（Giana / Giana_PSID /
R-Type 三首验证过），所以这个功能是纯增量。
