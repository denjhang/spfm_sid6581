# RP2350 直驱 SID —— 踩坑记录

> 2026-11-26。这份文档只记录**错误本身**，目的是让后来的人不重犯。
> 成果和最终方案见 [RP2350直驱SID_里程碑.md](RP2350直驱SID_里程碑.md)。
>
> 通篇下来，**没有一个是"RP2350 不好用"造成的**。全部是我自己的低级错误，
> 而且大部分属于"没先验证最小可动单元就直接堆功能"这一类。

---

## 一、USB 死机（BOOTSEL 指令发不进去）

这一类一共犯了两次，症状都是 `tools/rpfm_bootsel.exe` 报
`sid_rp2350 not found`，Windows 设备管理器里连 VID 2E8A 都看不到。

### 1.1 WS2812 状态机还没初始化就推数据

**错误代码**：

```c
ws_fill(0);                       // ← 先调用了
{
    uint o = pio_add_program(s_ws_pio, &ws2812_program);
    s_ws_sm = pio_claim_unused_sm(s_ws_pio, true);
    ws2812_program_init(s_ws_pio, s_ws_sm, o, PIN_WS2812, 800000, false);
}
```

**为什么死机**：`ws_fill()` 里面是 `pio_sm_put_blocking()`。
当状态机还没被 `pio_sm_init()` + `pio_sm_set_enabled()` 使能时，
它的 TX FIFO 永远不会被消费，`put_blocking` **永久阻塞**。
于是卡死在 `main()` 的第三行，`tud_init()` 根本没执行，USB 从未枚举。

**修法**：所有 WS2812 输出前加 `s_ws_ready` 闸门，初始化完成才允许推。

```c
static bool s_ws_ready = false;

static void ws_send(void) {
    if (!s_ws_ready) return;      // ← 这一行
    for (int i = 0; i < NUM_WS_LEDS; i++)
        pio_sm_put_blocking(s_ws_pio, s_ws_sm, s_ws_leds[i] << 8u);
}
```

**教训**：`pio_sm_put_blocking` 在没有使能的 SM 上是**死锁**，不是返回错误。
外设初始化顺序要倒过来想：**先让 SM 跑起来，再往里喂数据**。

### 1.2 把无限循环写在 `tud_task()` 前面

**错误代码**：

```c
s_ws_ready = true;
cs_select(0);
bus_ic_reset();

while (true) {                 // ← 这个循环里没有 tud_task()
    sid_boot_chime();
    sleep_ms(1200);
}

s_led_next = make_timeout_time_ms(500);
while (true) {                 // ← 永远到不了这里
    tud_task();
    ...
}
```

**为什么死机**：TinyUSB 不是中断驱动的，**必须持续调用 `tud_task()`** 才能响应
主机请求。进了第一个循环之后 USB 协议栈停摆，HID 设备从主机视角消失了，
所以 BOOTSEL 那帧发不进去。

**修法**：所有播放逻辑都放进同一个带 `tud_task()` 的循环里，
把"弹一个音"改成**非阻塞的一步**（`sid_arp_step()` 返回下次等待时间）。

```c
while (true) {
    tud_task();
    led_update();

    if (!s_sid_host_mode && time_reached(next_tune))
        next_tune = make_timeout_time_ms(sid_arp_step());

    ...
}
```

**教训**：裸机程序里，"播放音乐"这类长时间动作**不能写成阻塞循环**，
必须切成状态机的一步。`tud_task()` 的位置决定了 USB 是活是死。

### 1.3 操作失误：验证 HID 反而把板子打回 BOOTSEL

刷完固件之后我习惯再跑一次 `rpfm_bootsel.exe` 去"确认 HID 活着"。
**那条命令本身就是让板子进 BOOTSEL**，于是每次验证都把板子踢回烧录模式，
看起来像"板子自己在乱进 boot"。

**修法**：刷完之后不要发 BOOTSEL。要确认固件活着，看 **RP2350 盘符消失了**
就说明板子重启进了 app。

## 二、PIO 状态机不生效（A0 万用表恒为 0 V）

这是最耗时的一个，被分成了两层。

### 2.1 同一组引脚上起了第二个状态机

**错误来源**：RPFM 的 `pio_bus_init()` 原样照抄过来，它长这样：

```c
static void pio_bus_init(void) {
    uint offset = pio_add_program(s_bus_pio, &spfm_bus_write_program);
    s_bus_sm = pio_claim_unused_sm(s_bus_pio, true);
    spfm_bus_write_program_init(s_bus_pio, s_bus_sm, offset, PIN_BUS_BASE);

    // AY8910 dedicated SM — same program, clock div=32 for ~512ns per word
    s_ay_sm = pio_claim_unused_sm(s_bus_pio, true);
    ay8910_sm_init(s_bus_pio, s_ay_sm, offset, PIN_BUS_BASE);   // ← 同一个 offset
}
```

**为什么 A0 是死的**：两个状态机跑**同一个程序、绑同一组 GPIO0–10**。
PIO 的引脚输出是"最后写入者获胜"——两个 SM 都在 `out pins`，
AY 那个 SM 的输出把总线那个 SM 的输出覆盖掉。
AY 的分频是 32（~512 ns），总线是默认分频，所以实际引脚上是 AY 那个 SM 的
状态在主导，A0 恰好一直是 0。

**修法**：SID 不需要 AY，直接不启动那个 SM。

```c
// The AY8910 state machine is deliberately NOT started: it runs the same
// program on the same 11 pins, so a second enabled SM would fight this one
// for the bus.
```

删掉之后 **A0 立刻恢复翻转**，这是当时最关键的转折点。

**教训**：
- 一个 PIO 程序绑定一组 `out pins` 时，**只能有一个 SM 在跑**。
  多个 SM 分担不同引脚是可以的，重叠就会互相覆盖，而且**不报错**。
- 照抄别人的初始化函数时，要看清它到底起了几个 SM。

### 2.2 autopull 和显式 `pull block` 打架，每两个字丢一个

**错误代码**（RPFM 原文，我原样继承）：

```asm
.program spfm_bus_write
    pull block       ; 显式取一个字
    out pins, 11     ; 只输出低 11 位
```

```c
sm_config_set_out_shift(&c, true, /*autopull=*/true, /*threshold=*/32);
```

**为什么会丢字**：两条取数机制同时开着。

1. `pull block` 从 TX FIFO 取一个字到 OSR
2. `out pins, 11` 输出低 11 位，OSR 还剩 21 位
3. **autopull 发现 OSR 里不足 32 位，立刻又从 FIFO 取一个字塞进 OSR** ——
   把第 2 步剩下的位连同还没输出的内容一起冲掉
4. 回到 `pull block`，再取一个字，把第 3 步补进来的又覆盖掉

净效果：**每推两个 32 位字，只有一个真正到达引脚，而且位是错位的**。
地址相和数据相完全对不上，SID 一个有效写都没收到。

**修法**：关掉 autopull，只靠 `pull block`。

```c
sm_config_set_out_shift(&c, true, /*autopull=*/false, 32);
```

**教训**：`out pins, N` 配 autopull 时，**threshold 必须正好等于 N**。
要嘛设成 N，要嘛关掉。设成一个和 N 无关的数（比如 32）看起来能编过、
能跑、不报错，但数据会静默丢失——这是最难查的一类 bug。

### 2.3 1 µs 太快（物理层，不是逻辑层）

把上面两个修完之后，20 µs 一步能出声；1 µs 一步仍然完全无声。
6581 对写脉冲宽度有下限，而这条链上多了两级 245，边沿更缓。

**当前取值**：`SID_STEP_US 20`，照抄 `ym2413_pio_write_reg()` 的节奏，
一次寄存器写 7 个字 ≈ 140 µs。

**没做的事**：1 µs 到 20 µs 之间的下限没扫过。现在知道 autopull 那个 bug
也参与其中，所以实际上"1 µs 不行"这个结论**不干净**，需要重测。

## 三、PHI2 输出（最后解决的那个）

这一节单独讲，因为它是最后一个、也是最绕的一个。

### 3.1 最初的写法：sideset on nop

```asm
.program phi2_gen
.side_set 1 opt
.wrap_target
    nop side 1
    nop side 0
.wrap
```

```c
sm_config_set_sideset_pins(&c, pin);
sm_config_set_sideset(&c, 1, true, false);
sm_config_set_clkdiv(&c, clock_get_hz(clk_sys) / (2.0f * hz));
```

**结果**：GPIO14 上没有任何波形。万用表一直 0 V。

**为什么不工作**：`.side_set 1 opt` 让每条指令多一个可选的 sideset 位，
但 `nop side 1` 的编码依赖 pioasm 把 `.side_set` 的 opt/opt_en 配置正确展开。
在没有 `set pindirs` 显式建立输出方向的情况下，光靠 `pio_gpio_init` +
`sm_config_set_sideset_pins`，这个脚的实际驱动状态是不确定的。
（顺带：`pio_sm_set_consecutive_pindirs` 我写了，但顺序在 `pio_sm_init` 之前，
被 `pio_sm_init` 重置引脚时的行为影响。）

### 3.2 中途的错误尝试：用 PIO 做 2 Hz 慢闪

想在自检阶段让 GPIO14 慢速闪烁，肉眼确认脚是活的。写了：

```c
phi2_program_init(s_phi_pio, s_phi_sm, off, PIN_PHI2, 2.0f);   // 2 Hz
```

**不可能成功**：PIO 的 `clkdiv` 是 16.8 位定点，**上限 65535.9999**。
两条指令一个周期，所以最低频率是：

```
150 000 000 / (2 × 65536) ≈ 1144 Hz
```

2 Hz 差了三个数量级。这个参数会被静默截断到 1144 Hz，
肉眼看仍是"亮着不动"，反而更容易误判。

### 3.3 最终解法：抄 USBSID-Pico，改用 `set pins`

看 `refs/USBSID-Pico-master/src/pio/clock.pio` —— 同一个芯片（RP2350）、
对着真 SID 跑通的代码，它的写法是：

```asm
.program phi2_gen
.wrap_target
    set pins, 1       ; 高
    set pins, 0       ; 低
.wrap
```

```c
sm_config_set_set_pins(&c, pin, 1);          // ← set pins，不是 sideset
sm_config_set_clkdiv(&c, clock_get_hz(clk_sys) / (2.0f * hz));
pio_gpio_init(pio, pin);
pio_sm_set_consecutive_pindirs(pio, sm, pin, 1, true);
pio_sm_init(pio, sm, offset, &c);
pio_sm_set_enabled(pio, sm, true);
```

生成的机器码非常直白：

```
0xe001  set pins, 1
0xe000  set pins, 0
```

`set pins` 把引脚状态写进 SM 自己的输出寄存器，**不依赖 sideset 编码**，
也不依赖指令的可选位展开。这是它可靠的原因。

### 3.4 配套的自检：先 GPIO 慢闪，再交给 PIO

因为 3.2 那条路不通，最终把"验证引脚是活的"和"输出时钟"拆成两步：

```c
static void phi2_init(void) {
    /* 1) 纯 GPIO 慢闪 6 秒，肉眼/万用表可见 —— 证明这个脚本身能驱动 */
    gpio_init(PIN_PHI2);
    gpio_set_dir(PIN_PHI2, GPIO_OUT);
    for (int i = 0; i < 6; i++) {
        gpio_put(PIN_PHI2, 1);  sleep_ms(500);
        gpio_put(PIN_PHI2, 0);  sleep_ms(500);
    }

    /* 2) 交给 PIO，跑真实时钟 985248 Hz */
    s_phi_off = pio_add_program(s_phi_pio, &phi2_gen_program);
    s_phi_sm = pio_claim_unused_sm(s_phi_pio, true);
    phi2_program_init(s_phi_pio, s_phi_sm, s_phi_off, PIN_PHI2, PHI2_HZ_PAL);
}
```

这样"脚坏了"和"PIO 配错了"能一眼分开：前 6 秒不动就是硬件问题，
动了但没声才是 PIO 或后面的问题。

### 3.5 频率为什么用 985248 而不是 1 MHz

| 时钟 | 与 PAL 的标准时钟偏差 | 听感 |
|---|---|---|
| 1 000 000 Hz 晶振 | +15 000 ppm | **高 25.7 音分**，明显走音 |
| 985 248 Hz（PIO） | +24.6 ppm | **高 0.04 音分**，听不出来 |

分频算法：`150e6 / (2 × 985248) = 76.123`，PIO 的 16.8 位小数分频落在
`76 + 31/256`，实际输出 985 272 Hz。

**教训**：没有对应频率的晶振时，PIO 是比晶振更好的时钟源——精度高两个数量级，
而且省掉分压电阻（MCU 输出 3.3 V，6581 的 VIH 只要 2.0 V）。

## 四、其它一次性低级错误

| 错误 | 现象 | 原因 / 修法 |
|---|---|---|
| `PIN_WS2812` 照抄 RPFM 的 22 | 4 颗灯全灭 | 这块板的板载 WS2812 实际在 **GPIO16**（`3cf1d8b` 为 I2C 屏把代码改到 22，文档没跟着改）。分别只驱动 16 和 22 一次上机定论 |
| 改了 `out pins, 11` 但没改 `pack_bus()` 的掩码 | 地址永远只有 bit0 有效 | `(addr & 0x07) << 10` 要跟着改成 `(addr & 0x01) << 10` |
| `main.c` 里拼出两个连续的 `while (true)` | 第二个循环永远不执行 | 用脚本拼接代码段时没检查边界，编译照过 |
| `lcd.c` 用了 `malloc`/`free` 但没 `#include <stdlib.h>` | GCC 16 报 error（GCC 13 只是 warning） | 补 include。**新工具链会把老 warning 升级成 error** |
| PIO 的 `clkdiv` 想设成 2 Hz | 参数被静默截断到 ~1144 Hz | 见 §3.2，PIO 频率下限约 1144 Hz |
| 反复进 BOOTSEL 以为是固件 bug | 板子在 boot 和 app 之间来回 | 是我自己每次刷完又发了一次 BOOTSEL，见 §1.3 |

## 五、总教训

按重要性排：

1. **先让最小单元可见，再堆功能。**
   正确顺序应该是：GPIO 慢闪 → PIO 输出 2 个字的固定图案 → 单个寄存器写 →
   弹一个音 → 播一首。我把"PIO 移位 + 11 位总线 + USB + 播放器"一次全上了，
   出问题时分不清是哪个。

2. **底层总线第一版就该用最笨的 `gpio_put` 写出来。**
   这种时序问题用 PIO 提速是后面的事。先证明引脚会动，再谈时序精度。

3. **不报错的 bug 最贵。** 第二状态机抢引脚、autopull 丢字，两个都不报错、
   不崩溃、编译干净，只是"什么都没发生"。

4. **别人的初始化函数不能整段照抄。** RPFM 的 `pio_bus_init()` 里塞了 AY8910
   的 SM，对我们就是灾难。抄之前要逐行问"这一行对 SID 有意义吗"。

5. **同芯片、同目标的现成代码优先于自己的推导。**
   PHI2 最后是抄 USBSID-Pico 的 `clock.pio` 解决的。那个项目在同一颗 RP2350 上
   对着真 SID 跑通了，比我从 PIO 手册推导可靠得多。

6. **验证手段本身也会骗人。** "刷完再发一次 BOOTSEL 确认 USB 活着"这个动作，
   本身就把板子打回了 boot 模式。检查方法本身要先确认它不改变被测状态。
