# SID 6581 挂 SPFM：接线方案索引

> **✅ 已上机验证成功的方案：[接线表_374_02_min.md](接线表_374_02_min.md)**
> 四颗 IC（74LS374 + 74HCT02 + 74HCT32 + 74HC74）。
> 关键点有两个：① `TRIG_n` 同时驱动 SID 的 `/CS` 和 `R/W`（同源、零偏斜）；
> ② `TRIG_n` 必须再经 74HC74 整形缓冲成 `Wn` 才送 SID——实测跳过 74HC74
> 会让单次写入明显失真。移位寄存器（164/595/174/273）全部不需要。
>
> 先看那一份。本页只做索引和背景说明。

## 问题与解决过程

SID 只在 **PHI2 参与**下才锁存总线数据，而 SPFM 的 `/WR` 与模块上的 1 MHz 晶振
没有任何相位关系。早期接线把 `/CS` 和 `R/W` 分成两路（一路过两个 NOR 门、
一路裸接 `/WR`），两路不同源、有偏斜，单次写入经常丢失——表现为
"只有 `--repeat` ≥ 4 才能稳定出声，且音高不跟随指令"。

详细实测记录见 [写入时序调试记录.md](写入时序调试记录.md)。

**解决办法分两步**：

第一步，把写条件一次性编码成一个信号

```
TRIG_n = ¬A0 ∨ /WR ∨ CSn
```

它只在"数据相 + 本槽选中 + 正在写"时为低，正好就是 SID 的写使能。
把它**同时**驱动 `/CS`（pin6）和 `R/W`（pin7），两者同源、零偏斜、同进同出。

第二步，`TRIG_n` 不能直接接 SID，必须先过 74HC74 变成 `Wn`。
实测跳过这一级，单次写入会明显失真——74HC74 在这里做的是**信号再生**：
把带斜率、驱动 3 个负载的 `TRIG_n` 重新打成满幅度陡边沿，并顺势多给出约 30 ns 宽度。
理由和波形详见 [接线表_374_02_min.md](接线表_374_02_min.md) §5。

## 为什么当初设计得那么复杂

从 reDIP-SID 的 RTL 读到：

```systemverilog
w = ~bus_i.phi2 & ~bus_i.r_w_n && voice_cycle >= 1 && voice_cycle <= 6;
```

据此推断"写还必须落在内部 18 周期轮转的第 1–6 周期"，需要 ≥12 µs 的窗口才能保证命中，
于是设计了 PHI2 计数方案。**实测证明这个推断过于保守**：真实 6581 只需
"`/CS` 与 `R/W` 同时为低、跨过 PHI2 沿"，`/WR` 本身的宽度就够了。
18 周期轮转是芯片内部的写调度，不是总线侧必须满足的时序条件。

**教训：FPGA 软核 RTL 用于理解芯片行为，但硬件时序以实测为准。**

## 关于 74HC125

**不需要。** `TRIG_n` 只驱动 SID 的 `/CS` 和 `R/W` 两个 CMOS 输入，
一个 74HCT32 门输出带两路毫无压力。唯一说得上的用途是布线便利：
想让信号分两根线各走一处，用 125 的两个门（`/OE` 接 GND 常通）缓冲后分别送 pin6/pin7。
五份接线表里都标了这一步是可选的。

同理 **74HC245 / 574 / 573 也帮不上忙**：它们只影响地址锁存那一侧，
真正的问题是 `/CS` 与 `/R/W` 两路不同源、有偏斜。

## 接线表文件的维护方式

A–D 四份由 `tools/gen_wiring_docs.py` 一次生成，共用段落逐字一致。
改了脚本里的 `COMMON_HEAD` / `COMMON_TAIL` 后重新跑：

```bash
python tools/gen_wiring_docs.py
```

脚本会检查占位符是否全部替换。**不要单独手改某一份的共用段落**，否则四份会分叉。

最简方案 `接线表_374_02_min.md` 是手写的独立文件，不参与生成。
