# SID 6581 挂 SPFM：接线方案索引

> **✅ 已上机验证成功、且已验证到最简的方案：[接线表_374_02_min.md](接线表_374_02_min.md)**
> **三颗 IC**（74LS374 + 74HCT02 + 74HCT32）。
>
> ```
> LE     = NOR(A0, /WR)              → 374 CLK
> TRIG_n = ¬A0 ∨ /WR ∨ CSn           → SID pin6 (/CS)
> SPFM /WR                           → SID pin7 (R/W)      // 裸线
> ```
>
> 不需要 74HC74，不需要移位寄存器，不需要单稳态。
>
> 先看那一份，本页只做索引和背景说明。

## 一路走到最简的过程

这个问题被误判过两次，两次都是把推测当成了结论。记在这里免得再走一遍。

### 第一次误判：以为需要 13–14 µs 的写窗口

从 reDIP-SID 的 RTL 读到：

```systemverilog
w = ~bus_i.phi2 & ~bus_i.r_w_n && voice_cycle >= 1 && voice_cycle <= 6;
```

据此推断“写还必须落在内部 18 周期轮转的第 1–6 周期”，于是设计了用 PHI2 计数
把窗口拉到 13–14 µs 的电路（164 / 595 / 174 / 273 四份方案）。

**实测否定**：真实 6581 的 `/WR` 窗口只占 PHI2 周期的 20%，如果真要求跨过上升沿
就该有 80% 丢写，而现在是稳定写入。那 18 周期轮转是 FPGA 软核**内部**的写调度，
不是总线侧要求。

### 第二次误判：以为 74HC74 不可省

拆掉 74HC74、把 `TRIG_n` **同时**接 `/CS` 和 `R/W` 时，单次写入明显失真，
于是得出“74HC74 是必需的整形器”的结论。

**实际原因是驱动能力**：一个 74HCT32 输出带两个 SID CMOS 输入外加走线电容，
边沿被拖慢。把两条线分开——`TRIG_n` 只带 `/CS`，`/WR` 直接带 `R/W`——问题消失，
74HC74 可以拆掉，无任何副作用。

### 现在的认识

**6581 在这里就是异步写器件**：`/CS` 与 `R/W` 同时为低就锁存，和 YM2163 / YM7129
没有本质区别。datasheet 里 `TW` 的措辞（“从 φ2、CS、R/W 三者中最晚发生的那一个开始算”）
是针对标准 C64 时序的保守描述，不构成“必须等 PHI2”的约束。

**唯一必须保住的**是 `TRIG_n` 里的 `¬A0`：地址相时 `/CS` 必须为高，
否则会在 374 锁地址的同时误写，表现为每次改频率都咔嗒一声。

**教训：FPGA 软核 RTL 可以解释芯片行为，但硬件时序只能以实测为准；
一次实测失败要问“是不是还有别的变量没控制”，而不是直接归因到某个器件。**

## 关于 74HC125 / 245 / 574 / 573

**都不需要。** `TRIG_n` 只驱动 SID 的 `/CS` 一个 CMOS 输入，一个 74HCT32 门绰绰有余；
`R/W` 由 `/WR` 直接驱动，负载更轻。245 / 574 / 573 只影响地址锁存那一侧，与本问题无关。

早期版本提过“74HC125 可以让 `TRIG_n` 分成两根线各带一个负载”——那是为了解决
一个门带两个负载时边沿变慢的问题。现在两条线本来就分开，这个需求不存在了。

## 接线表文件的维护方式

A–D 四份由 `tools/gen_wiring_docs.py` 一次生成，共用段落逐字一致。
改了脚本里的 `COMMON_HEAD` / `COMMON_TAIL` 后重新跑：

```bash
python tools/gen_wiring_docs.py
```

脚本会检查占位符是否全部替换。**不要单独手改某一份的共用段落**，否则四份会分叉。

最简方案 `接线表_374_02_min.md` 是手写的独立文件，不参与生成。
