# 三种接法能不能用：RP2350A 接 SID 6581 的时序实测

> 2026-11-26。面包板上的三种接法，用真实 `.sid` / `.sidvgm` 数据判断哪个能用、
> 哪个有问题。对照 `refs/USBSID-Pico-master`。
>
> **结论：三种都能用，没有一种有时序硬伤。** 判据是一个很硬的数——`.sidvgm` 的
> 时间戳都是整数 tick，所以**最小非零写间隔就是 1 tick = 22.676 µs**，而三种接法的
> 单写耗时都在这条线以下（18.90 / 18.90 / 15.85 µs）。只要单写比 22.676 µs 快，
> 任何间隔都不可能被压缩。
>
> 唯一真实的约束是 **`SID_HOLD` 不能超过某个上限**（现方案 15，直驱 18），
> 现在的 12 在两种接法下都有余量。**这不是"必须改电路"，是"别把 hold 调大"。**

---

## 1. 三种接法

| | A | B | C |
|---|---|---|---|
| 接法 | 374 + 02 + 32（现在） | A 但 CS 焊死 GND | 照 USBSID 直驱，无锁存 |
| 逻辑 IC | 3 片 | 3 片（32 的 CS 输入接地） | **0 片** |
| 地址线 | D0–D4 分时复用 + 374 锁存 | 同 A | A0–A5 专用 GPIO，与数据同一字 |
| 每写字数 | 3 + hold + 2 | **完全相同** | 1 + hold + 1 |
| 单写耗时（hold=12） | **18.90 µs** | **18.90 µs** | **15.85 µs** |
| 现在能不能出声 | ✅ 已上机 | ✅ 等价 | 需改固件引脚表 |

**A 和 B 时序完全一样**，因为 `write_reg_sid()` 每次写都 `cs_select(0)` 但从不拉回，
所以 CS0# 本来就是常量 0（`main.c:377`，细节见 §5）。把 CS 引脚焊到 GND 只是把
固件里已经在做的事变成硬件事实，**一个纳秒都不变**。

---

## 2. 判据：1 tick = 22.676 µs

`.sidvgm` 的时间基是 44100 Hz（VGM 写死的），所以时间戳只能落在
`n × 22.676 µs` 的网格上。实测确认（四首代表曲合并统计）：

```
非零间隔的最小值 = 1 tick = 22.676 µs
所有非零间隔都是它的整数倍    ✅
```

于是**任何非零的写间隔都至少是 22.676 µs**。只要单写耗时低于这条线，
固件的 `deadline += dt; fire = max(deadline, now)` 就永远不需要跳过错过的时刻，
时间轴逐条精确。

三种接法的实测/推算单写耗时：

| 接法 | 字数（hold=12） | 1 字 = 1 PHI2 = 1.015 µs | 固定开销 | 合计 | 距 22.676 µs |
|---|---|---|---|---|---|
| A / B | 3+12+2 = 17 | 17.25 µs | 1.65 µs | **18.90 µs** | 还有 3.78 µs |
| C | 1+12+1 = 14 | 14.21 µs | 1.64 µs | **15.85 µs** | 还有 6.82 µs |

> 18.90 µs 是 `build/wbench.exe 4000` 在板上实测的；固定开销由它反推。

**C 比 A/B 快的 3 µs，全部来自取消了地址相的那两个字。**

## 3. RoboCop 3 —— 普通 PSID，逐帧看

`sidvgm/rsid/RoboCop_3/` 20 首全部是 167 s 的完整录制，CIA 2-frame 定时
（`speed=$00010000`，`play=$1FC0`），属于最典型的一类普通 PSID。

### 3.1 它的结构

```
每个视频帧（19.73 ms）开头：22~27 条写挤在 1~2 个 tick 内
之后：                      19.71 ms 完全没有写
```

实测：

| 项 | 数值 |
|---|---|
| 时刻组大小（同一 tick 内的写数） | 分布只有 1 / 2 / 3 / 26 四种，中位 2 |
| 最大连发 | **26 条**，占 0.61 ms |
| 连发之后的空档 | 中位 **19.73 ms**（正好一帧） |
| 每帧写数 | 中位 22，**最大 49** |
| 最坏一帧需要的总线时间 | 49 × 18.9 µs = **0.93 ms / 19.73 ms = 4.7%** |
| 每帧余量 | 19.73 ms ÷ 18.9 µs = 1044 次，实际最多 49 次 → **21 倍** |

关键点：**这 22~27 条连发写的是不同寄存器**（一次扫整个 `$D400-$D418`），
各寄存器独立锁存，先后顺序对声音没有影响。实测 92634 个时刻组里，
**92633 个组内寄存器全不同**，只有 1 个组有重复。

所以"连发"在这里完全不需要担心：0.61 ms 写完，剩下 19.1 ms 什么都不做。

### 3.2 相邻间隔

| 间隔 | 次数 | 占比 | 说明 |
|---|---|---|---|
| 0 tick（同一时刻） | 91445 | 49.7% | 扫寄存器，见上 |
| 1 tick = 22.68 µs | 84267 | 45.8% | 逐条写，比任何接法的单写都快 |
| 869~871 tick ≈ 19.71 ms | 8364 | 4.5% | 帧间空档 |

**间隔 < 18.9 µs 的：0 个。间隔 < 15.85 µs 的：0 个。**
也就是说 RoboCop 3 这种曲子在 A/B/C 三种接法下**都是逐条精确的**，
连"偶尔晚一点"都不会发生。

## 4. 全曲库 697 首的验证

按固件真实的 deadline 行为（`deadline += dt; fire = max(deadline, now); now = fire + 单写耗时`）
回放全部 697 个 `.sidvgm`：

| 指标 | A / B（18.90 µs） | C（15.85 µs） |
|---|---|---|
| 调度滞后（写晚于乐谱）中位 | **0.208 ms** | 0.138 ms |
| 调度滞后 最坏 | **1.493 ms** | 1.253 ms |
| 滞后 > 5 ms 的写 | **0 次** | 0 次 |
| 滞后 > 20 ms 的写 | **0 次** | 0 次 |
| 总时长 vs 乐谱 中位 | **+0.0000%** | +0.0000% |
| 总时长 vs 乐谱 最坏 | **+0.1133%** | +0.0817% |

最坏 1.5 ms 滞后出现在 `Arkanoid_s09~s20`，都是同一批小文件。

**为什么总时长几乎不变**：固件是 deadline 累加器，晚一条不会累积误差——下一条的
deadline 已经追上来了，它会立刻发出（dt 视为 0），于是自动补齐。所以"单写比间隔慢"
不会让整曲变慢，只会让那一个瞬间的几条写挤在一起。

每帧总线占用（最坏情况）：

| 占用率 | 曲子 |
|---|---|
| 19.8% | `turboutrun_s02`（207 次/帧） |
| 19.4% | `Arkanoid_s01`（203 次/帧） |
| 17.4% | `Echofied_6581_s03`（182 次/帧） |
| **中位 4.7%** | — |
| **超 100% 的曲子** | **0 / 697** |

## 5. A 和 B 为什么完全相同

`main.c:377`，`write_reg_sid()` 第一句是 `cs_select(0)`：

```c
static inline void write_reg_sid(uint8_t addr, uint8_t data) {
    uint8_t a = (uint8_t)(addr & 0x1F);
    cs_select(0);                                   /* ← 拉低，但从不拉回 */
    sid_pio_write_reg(s_bus_pio, s_bus_sm, a, data, s_sid_hold);
```

`CS_IDLE 0x03` 只在 `pio_cs_init()` 里用一次（`main.c:115`），之后没有任何地方
把它拉回。所以从第一次写开始，**CS0# 恒等于 0**。

代进你的逻辑：

```
TRIG_n = ¬A0 ∨ /WR ∨ CSn     CSn=0     TRIG_n = ¬A0 ∨ /WR
```

CS 项彻底消失。**把 CS 那根线焊到 GND，电路行为逐周期相同**，因为固件早就把它
当 0 用了。

这件事唯一的影响：片选线现在不承担任何选择工作，**多片 SID 靠它是选不出来的**
（而且 `LE = NOR(A0,/WR)` 不看 CS，多片时会串片）。上游也确实直接拒绝
（`src/sid_lsfp.cpp:257`、`:411`，`sidChips() > 1` 报错）。
曲库里有 `sid/rsid/Anthrox_2SID.sid`、`sid/rsid/Hokuto_Stereo_2SID.sid` 两首跑不了。

## 6. C 接法（直驱）的实测收益

照 USBSID 的做法：数据线和地址线是**同一个 PIO 字**，控制线是另一个 3 位字。

```c
sm_config_set_out_pins(&c_data,    D0, A5 + 1);   /* 0..13，14 根 */
sm_config_set_out_pins(&c_control, RW, 3);        /* 19..21 */
data_word = ((address & 0x1F) << 8) | data;       /* bus.c:98：地址和数据一起出去 */
```

| 项 | A / B | C |
|---|---|---|
| 逻辑 IC | 3 片 | **0 片**（面包板上少 3 片、少 12 根跳线） |
| 单写耗时 | 18.90 µs | **15.85 µs** |
| 单写上限（不能超过 22.676 µs） | hold ≤ **15** | hold ≤ **18** |
| 全库最坏滞后 | 1.493 ms | 1.253 ms |
| 全库最坏时长偏差 | +0.113% | +0.082% |
| 多片 SID | 串片，不可用 | 每片独立 CS，可用 |

**注意 C 的真实收益不是"更快所以更好听"**——A 已经够快了。C 的收益是：
面包板上少 3 颗 IC 和一堆跳线（接触不良是面包板的主要故障源），以及多片 SID 终于
能跑。速度提升只是副产品。

## 7. 唯一真正需要守的约束：SID_HOLD

单写耗时 = 固定开销 + (字数) × 1.015 µs。hold 一大就超过 22.676 µs，那时候
1-tick 的连发就会被压。这是三种接法共同的悬崖：

| hold | 单写耗时 | A / B | C |
|---|---|---|---|
| 6 | 12.81 µs | ✅ | ✅ |
| 10 | 16.87 µs | ✅ | ✅ |
| **12（现在）** | **18.90 µs** | ✅ 余 3.78 µs | ✅ 余 6.82 µs |
| 15 | 21.94 µs | ⚠️ 余 0.74 µs | ✅ |
| **16** | 22.96 µs | ❌ 超过 1 tick | ✅ |
| **18** | 24.99 µs | ❌ | ⚠️ 余 −2.3 µs |
| 24 | 31.08 µs | ❌ | ❌ |

实测全库：hold ≤ 15 时**没有任何一条写被推迟**；hold=16 起立刻有 30.8% 的写
被推迟。也就是说 **hold=12 是安全区中间偏保守的位置，不是刚好卡在边上。**

这就是为什么上一轮把 hold 从 1 调到 12 之后 digi 就正常了——不是因为 12 有什么
魔力，而是因为 12 在 22.676 µs 这条线以下留了 3.78 µs 余量，而 hold=1 时数据相
只有 1.015 µs，SID 内部来不及锁存。

---

## 8. 结论

**1. 三种都能用，不需要为时序改电路。**

判据是 `.sidvgm` 的 1 tick = 22.676 µs 最小非零间隔。A/B 的 18.90 µs 和 C 的
15.85 µs 都在它下面，所以任何间隔都不会被压缩。全库 697 首里，滞后 > 5 ms 的写
是 **0 次**，总时长偏差中位数 **0.0000%**，最坏 **0.11%**。

**2. A 和 B 逐周期等价。**

`cs_select(0)` 从不拉回，CS0# 本来就是常量 0，所以把 CS 焊死 GND 不会有任何变化。
B 唯一的实际意义是"承认这个事实"——但你既不会因此省引脚（GPIO12 已经占了），
也不会因此跑得更快。**建议 A 保持不动。**

**3. C 值得做，但不急。**

面包板上少 3 颗 IC 和 12 根跳线，这对接触可靠性是实实在在的收益；顺带把多片 SID
打通。速度上它比 A 快 3 µs，但 A 已经不缺这 3 µs 了，所以**不要为了速度去改**。

**4. 真正要守的是 hold ≤ 15（现方案）/ ≤ 18（直驱）。**

`CMD_SID_STEP` 现在可以设到 32，但 A/B 接法下超过 15 就会开始压 1-tick 连发。
如果哪天要把 hold 调大（比如换更慢的 SID 或更长的排线），先确认没超过 22.676 µs。
